Question 9 / 201

You deploy a new release of an internal application during a weekend maintenance window when there is minimal user traffic. After the window ends, you learn that one of the new features isn't working as expected in the production environment. After an extended outage, you roll back the new release and deploy a fix. You want to modify your release process to reduce the mean time to recovery so you can avoid extended outages in the future.

What should you do? (Choose two.)

  • A. Before merging new code, require 2 different peers to review the code changes.
  • B. Adopt the blue/green deployment strategy when releasing new code via a CD server.
  • C. Integrate a code linting tool to validate coding standards before any code is accepted into the repository.
  • D. Require developers to run automated integration tests on their local development environments before release.
  • E. Configure a CI server. Add a suite of unit tests to your code and have your CI server run them on commit and verify any changes.
Show Suggested Answer
Suggested Answer: BE 
Odpowiedź: B, E.

Wyjaśnienie:
Głównym celem zadania jest skrócenie średniego czasu przywracania sprawności (MTTR - Mean Time To Recovery). Oznacza to, że musimy skupić się na rozwiązaniach, które pozwalają szybciej wykryć błąd lub błyskawicznie cofnąć zmiany (rollback), gdy coś pójdzie nie tak.

Dlaczego odpowiedzi B i E są poprawne:
B. Strategia Blue/Green deployment polega na utrzymywaniu dwóch identycznych środowisk produkcyjnych. W danym momencie tylko jedno (np. Blue) obsługuje ruch. Nowa wersja jest wdrażana na środowisko Green. Jeśli po przełączeniu ruchu okaże się, że wersja Green ma błędy, powrót do wersji Blue (rollback) polega jedynie na zmianie konfiguracji Load Balancera, co dzieje się niemal natychmiastowo. To drastycznie skraca MTTR.
E. Serwer CI (Continuous Integration) z zestawem testów jednostkowych (unit tests) uruchamianych przy każdym commicie pozwala na natychmiastowe wykrycie regresji w kodzie. Choć testy jednostkowe kojarzą się głównie z zapobieganiem błędom (Change Failure Rate), w kontekście MTTR posiadanie zautomatyzowanego pipeline'u pozwala na szybsze i bezpieczniejsze przygotowanie oraz wdrożenie poprawki (fix), jeśli błąd jednak trafi na produkcję.

Dlaczego pozostałe opcje są błędne:
A. Wymaganie dwóch osób do code review (peer review) to doskonała praktyka poprawiająca jakość kodu, ale jest to proces czysto manualny i prewencyjny. Nie przyspiesza on procesu odzyskiwania sprawności po wystąpieniu awarii na produkcji.
C. Linting (sprawdzanie standardów kodowania) pomaga utrzymać czystość kodu, ale nie ma żadnego wpływu na szybkość przywracania usług po awarii spowodowanej błędem logicznym w nowej funkcjonalności.
D. Uruchamianie testów lokalnie przez deweloperów jest mało wiarygodne (problem "u mnie działa") i nie daje gwarancji, że te same testy przejdą w środowisku produkcyjnym. Brakuje tu centralizacji i powtarzalności, którą daje serwer CI.

Hity i triki:
- Zapamiętaj 4 metryki DORA: Deployment Frequency, Lead Time for Changes, Change Failure Rate, Time to Restore Service (MTTR).
- Jeśli widzisz "MTTR", szukaj odpowiedzi związanych z: Rollback, Blue/Green, Canary, Monitoring/Alerting.
- Jeśli widzisz "Change Failure Rate", szukaj: CI, Testing, Code Review, Linting.
- Szybki rollback jest zawsze lepszy dla MTTR niż "fix forward" (naprawianie na żywo).

Analiza i Podsumowanie Dyskusji (AI)

Zarządzanie czasem odzyskiwania (MTTR) wymaga inwestycji w automatyzację procesów zarówno prewencyjnych (testy w CI), jak i operacyjnych (strategie wdrożeń jak Blue/Green).

💡 Wskazówki i Triki (Exam Tips)

  • MTTR to szybkość powrotu do normy: Szukaj mechanizmów, które skracają czas przestoju.
  • Błędy na produkcji: Nawet przy najlepszych testach błędy się zdarzają. System musi być zaprojektowany tak, aby porażka była tania i szybka do odwrócenia.
  • Automatyzacja vs Proces: Automatyczne przełączanie ruchu (B) i automatyczne budowanie (E) zawsze wygrywają z manualnym sprawdzaniem kodu (A) w pytaniach o szybkość operacyjną.

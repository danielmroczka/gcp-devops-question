Question 56 / 201

Cloud Build

You use Cloud Build to build your application. You want to reduce the build time while minimizing cost and development effort.

What should you do?

  • A. Use Cloud Storage to cache intermediate artifacts.
  • B. Run multiple Jenkins agents to parallelize the build.
  • C. Use multiple smaller build steps to minimize execution time.
  • D. Use larger Cloud Build virtual machines (VMs) by using the machine-type option.
Show Suggested Answer
Suggested Answer: A 
Poprawna odpowiedź: A. Use Cloud Storage to cache intermediate artifacts.

Wyjaśnienie:
Największym "złodziejem" czasu w procesach CI/CD jest wielokrotne pobieranie tych samych zależności (np. `node_modules`, biblioteki Maven/Gradle) oraz ponowne kompilowanie niezmienionego kodu. Cloud Build nie posiada wbudowanego, automatycznego cache'u stanowego między uruchomieniami, dlatego najlepszą praktyką jest wykorzystanie Cloud Storage do przechowywania skompresowanych paczek z zależnościami. Na początku buildu pobieramy cache z GCS, a na końcu (jeśli zaszły zmiany) wysyłamy nową wersję z powrotem. Pozwala to na drastyczne skrócenie czasu buildu przy minimalnym koszcie za storage.

Dlaczego inne odpowiedzi są błędne:
- B: Jenkins agents: Jenkins to zupełnie inne narzędzie. Pytanie dotyczy optymalizacji Cloud Build. Przeniesienie całego workflow do Jenkinsa wymagałoby ogromnego wysiłku deweloperskiego i zwiększyłoby koszty utrzymania infrastruktury.
- C: Multiple smaller build steps: Zbyt duża liczba małych kroków może wręcz spowolnić build ze względu na narzut (overhead) związany z uruchamianiem każdego kontenera dla danego kroku. Optymalizacja powinna polegać na łączeniu logicznych operacji.
- D: Larger Cloud Build VMs: Zwiększenie typu maszyny (np. na `n1-highcpu-32`) przyspieszy kompilację, ale znacznie zwiększy koszt za każdą minutę działania buildu. Pytanie prosi o minimalizację kosztów, a caching (opcja A) jest zazwyczaj tańszy i daje lepsze rezultaty przy powtarzalnych buildach.

Hity i triki (GCP DevOps Exam):
- Kaniko: Jeśli Twoim głównym problemem jest czas budowania obrazów Docker, Cloud Build wspiera "Kaniko cache". Pozwala on na przechowywanie warstw obrazu w rejestrze (Artifact Registry), co przyspiesza instrukcje RUN w Dockerfile.
- Wybór regionu: Uruchamiaj buildy w tym samym regionie, w którym masz Artifact Registry i Cloud Storage, aby uniknąć opłat za transfer danych i zmniejszyć opóźnienia.
- Parallel steps: Możesz uruchamiać kroki równolegle w Cloud Build, używając pola `waitFor`. Jeśli Twoje testy jednostkowe i linting nie zależą od siebie, uruchom je w tym samym czasie!

Analiza i Podsumowanie (GCP DevOps Expert)

Optymalizacja Cloud Build to balansowanie między szybkością (Build Minutes) a kosztami. Caching jest najbardziej efektywną techniką, ponieważ pozwala uniknąć wykonywania tej samej pracy wielokrotnie.

💡 Kluczowe wnioski:

  • GCS for Cache: Standardowy wzorzec: 1. Pobierz archiwum z GCS. 2. Rozpakuj. 3. Build. 4. Spakuj i wyślij do GCS.
  • Machine Type: Używaj większych maszyn tylko wtedy, gdy Twój kod faktycznie potrafi wykorzystać wiele rdzeni (np. kompilacja C++/Java z flagami parallel).
  • Artifact Registry: Zawsze używaj Artifact Registry zamiast starego Container Registry dla lepszej wydajności i integracji.

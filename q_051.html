Question 51 / 201

Postmortem SLI SLO

You support a stateless web-based API that is deployed on a single Compute Engine instance in the europe-west2-a zone. The Service Level Indicator (SLI) for service availability is below the specified Service Level Objective (SLO). A postmortem has revealed that requests to the API regularly time out. The time outs are due to the API having a high number of requests and running out memory. You want to improve service availability.

What should you do?

  • A. Change the specified SLO to match the measured SLI
  • B. Move the service to higher-specification compute instances with more memory
  • C. Set up additional service instances in other zones and load balance the traffic between all instances
  • D. Set up additional service instances in other zones and use them as a failover in case the primary instance is unavailable
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Poprawną odpowiedzią jest C, ponieważ skalowanie horyzontalne (dodawanie kolejnych instancji) oraz rozmieszczenie ich w wielu strefach (High Availability) bezpośrednio rozwiązuje problem przeciążenia pojedynczej maszyny i niskiej dostępności usługi.

1. **C (Set up additional service instances in other zones and load balance the traffic):** 
   - **Skalowanie horyzontalne:** Dodanie większej liczby instancji pozwala rozłożyć ruch na wiele maszyn, co rozwiązuje problem braku pamięci (OOM - Out of Memory) wynikający z dużej liczby żądań na pojedynczym serwerze.
   - **Wysoka dostępność (HA):** Umieszczenie instancji w różnych strefach (Multi-zone) chroni usługę przed awarią całej strefy. Użycie Load Balancera zapewnia automatyczne kierowanie ruchu tylko do "zdrowych" instancji. To rozwiązanie jest najbardziej zgodne z praktykami SRE w celu poprawy SLO dostępności.

Analiza niepoprawnych odpowiedzi:
- **A (Change the specified SLO to match the measured SLI):** Jest to błąd procesowy. SLO powinno odzwierciedlać potrzeby biznesowe i oczekiwania użytkowników. Jeśli system nie spełnia SLO, należy poprawić system, a nie obniżać wymagania ("moving the goalposts").
- **B (Move the service to higher-specification compute instances):** Jest to skalowanie pionowe (Vertical Scaling). Choć może tymczasowo pomóc z brakiem pamięci, nadal pozostawia usługę na pojedynczym punkcie awarii (Single Point of Failure). Jeśli ta jedna, większa maszyna ulegnie awarii, usługa całkowicie przestanie działać.
- **D (Set up additional service instances... as a failover):** Model failover (Active-Passive) jest mniej efektywny niż Load Balancing (Active-Active). W modelu failover instancja zapasowa marnuje zasoby, czekając na awarię głównej, zamiast pomagać w obsłudze dużego ruchu, który jest przyczyną problemów z pamięcią.

Hity i triki (Hints & Tricks):
- **SLI (Indicator):** To co mierzysz (np. % udanych zapytań).
- **SLO (Objective):** Cel, który chcesz osiągnąć (np. 99.9%).
- **Error Budget:** To 100% - SLO. Jeśli Twój SLI spada poniżej SLO, Twój budżet błędów został przekroczony i musisz skupić się na poprawie niezawodności zamiast na wdrażaniu nowych funkcji.
- W chmurze zawsze preferuj **Horizontal Scaling** (skalowanie horyzontalne) nad Vertical Scaling.

Analiza i Podsumowanie Dyskusji (AI)

Pytanie łączy wiedzę o architekturze systemów (skalowanie) z procesami SRE (postmortem, SLO). Diagnoza wskazuje na dwa problemy: brak zasobów pod obciążeniem oraz brak odporności na awarie.

💡 Wskazówki i Triki (Exam Tips)

  • Jeśli aplikacja jest "stateless" (bezwidokowa), skalowanie horyzontalne jest prawie zawsze poprawnym wyborem.
  • "Single instance" w chmurze to zawsze ryzyko. Rozwiązania wysokiej dostępności (HA) wymagają co najmniej dwóch instancji w różnych strefach.
  • Load Balancer to fundament dla poprawy SLI dostępności i latencji w GCP.

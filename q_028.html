Question 28 / 201

Terraform

You are responsible for creating and modifying the Terraform templates that define your Infrastructure. Because two new engineers will also be working on the same code, you need to define a process and adopt a tool that will prevent you from overwriting each other's code. You also want to ensure that you capture all updates in the latest version.

What should you do?

  • A. Store your code in a Git-based version control system. Establish a process that allows developers to merge their own changes at the end of each day. Package and upload code to a versioned Cloud Storage bucket as the latest master version.
  • B. Store your code in a Git-based version control system. Establish a process that includes code reviews by peers and unit testing to ensure integrity and functionality before integration of code. Establish a process where the fully integrated code in the repository becomes the latest master version.
  • C. Store your code as text files in Google Drive in a defined folder structure that organizes the files. At the end of each day, confirm that all changes have been captured in the files within the folder structure. Rename the folder structure with a predefined naming convention that increments the version.
  • D. Store your code as text files in Google Drive in a defined folder structure that organizes the files. At the end of each day, confirm that all changes have been captured in the files within the folder structure and create a new .zip archive with a predefined naming convention. Upload the .zip archive to a versioned Cloud Storage bucket and accept it as the latest version.
Show Suggested Answer
Suggested Answer: B 
Odpowiedź: B.

Wyjaśnienie:
Poprawna odpowiedź to B. W pracy zespołowej nad kodem infrastruktury (Infrastructure as Code - IaC), standardem jest traktowanie plików konfiguracyjnych (np. Terraform) tak samo jak kodu aplikacji. Użycie systemu kontroli wersji opartego na Gicie (np. Cloud Source Repositories, GitHub, GitLab) umożliwia równoległą pracę wielu osób, śledzenie historii zmian i rozwiązywanie konfliktów. Proces Code Review (przegląd kodu przez współpracowników) oraz testy (np. `terraform validate`, `tflint`) przed scaleniem do głównej gałęzi (master/main) gwarantują spójność, bezpieczeństwo i wysoką jakość "źródła prawdy" o infrastrukturze.

Dlaczego inne odpowiedzi są błędne:
A. Scalanie zmian tylko na koniec dnia prowadzi do dużych i trudnych do rozwiązania konfliktów (merge conflicts). Pakowanie kodu w archiwa i przesyłanie do Cloud Storage jest nieefektywne i nie zastępuje profesjonalnego przepływu pracy opartego na Gicie.
C i D. Google Drive absolutnie nie nadaje się do zarządzania kodem źródłowym. Brakuje w nim mechanizmów różnicowania (diff), scalania (merge) oraz integracji z narzędziami automatyzacji (CI/CD). Przechowywanie wersji w folderach lub plikach .zip to ogromny "Toil" (mozolna, powtarzalna praca), który zwiększa ryzyko błędów ludzkich.

Hity i triki (Exam Tips):
- Słowa klucze dla IaC: "Git-based VCS", "Code Review", "CI/CD", "Pull Requests".
- Pamiętaj: W Terraformie kluczowe jest również użycie **Remote Backend** (np. GCS) z włączonym blokowaniem stanu (State Locking), aby uniknąć jednoczesnych modyfikacji tej samej infrastruktury przez różne osoby.
- Git zapewnia nie tylko kontrolę wersji, ale również "audytowalność" – dokładnie wiemy, kto, kiedy i dlaczego zmienił dany element infrastruktury.

Analiza i Podsumowanie Dyskusji (AI)

Zarządzanie infrastrukturą jako kodem (IaC) wymaga dyscypliny inżynierskiej. Git nie jest tylko narzędziem do zapisu plików, ale fundamentem całego cyklu życia DevOps, umożliwiającym współpracę i automatyzację (GitOps).

💡 Wskazówki i Triki (Exam Tips)

  • Version Control: Wszystko (kod, testy, konfiguracja, skrypty wdrożeniowe) powinno być w Gicie.
  • Code Review: To najlepszy sposób na dzielenie się wiedzą w zespole i wykrywanie błędów przed ich trafieniem na produkcję.
  • Automatyzacja: Każdy commit do głównej gałęzi powinien wyzwalać automatyczne testy i opcjonalnie wdrożenie.

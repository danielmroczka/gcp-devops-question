Question 62 / 201

Jenkins

Your application runs on Google Cloud Platform (GCP). You need to implement Jenkins for deploying application releases to GCP. You want to streamline the release process, lower operational toil, and keep user data secure.

What should you do?

  • A. Implement Jenkins on local workstations.
  • B. Implement Jenkins on Kubernetes on-premises.
  • C. Implement Jenkins on Google Cloud Functions.
  • D. Implement Jenkins on Compute Engine virtual machines.
Show Suggested Answer
Suggested Answer: D 
Poprawna odpowiedź: D. Implement Jenkins on Compute Engine virtual machines.

Wyjaśnienie:
Uruchomienie Jenkinsa na Google Compute Engine (GCE) jest standardowym sposobem na wdrożenie tego narzędzia w chmurze Google, gdy nie korzystamy z gotowych rozwiązań SaaS. Pozwala to na pełną integrację z ekosystemem GCP. Kluczowym aspektem bezpieczeństwa i redukcji "toil" jest tutaj wykorzystanie **Instancyjnych Kont Serwisowych (Service Accounts)**. Dzięki nim Jenkins może uwierzytelniać się w API Google Cloud bez konieczności ręcznego zarządzania kluczami JSON, co znacznie podnosi poziom bezpieczeństwa i ułatwia automatyzację.

Dlaczego inne odpowiedzi są błędne:
- A: Implement Jenkins on local workstations: Rozwiązanie skrajnie niebezpieczne i nieprofesjonalne. Brak centralizacji, brak backupów, trudności w skalowaniu i ogromne ryzyko wycieku poświadczeń z lokalnej maszyny.
- B: Implement Jenkins on Kubernetes on-premises: Chociaż Kubernetes jest świetny dla Jenkinsa, utrzymywanie klastra "on-premises" (lokalnie) do zarządzania zasobami w chmurze zwiększa opóźnienia i nakład pracy operacyjnej (Toil) związany z utrzymaniem własnej infrastruktury serwerowej.
- C: Implement Jenkins on Google Cloud Functions: Cloud Functions to usługa typu FaaS, stworzona do krótkich, bezstanowych zadań. Jenkins jest ciężką, stanową aplikacją, która wymaga ciągłego działania mastera, co wyklucza użycie GCF.

Hity i triki (GCP DevOps Exam):
- Service Accounts over Keys: Nigdy nie wgrywaj kluczy `.json` kont serwisowych do Jenkinsa, jeśli działa on na GCP. Przypisz odpowiednie uprawnienia bezpośrednio do maszyny VM (lub podu GKE).
- Cloud Build as an alternative: W egzaminie warto pamiętać, że Google często promuje własne rozwiązanie "Cloud Build" jako bardziej "Cloud Native" i bezobsługowe (serverless) niż Jenkins.
- Jenkins on GKE: Chociaż nie było tego w opcjach, uruchomienie Jenkinsa na GKE jest bardzo popularne, ponieważ pozwala na automatyczne tworzenie efemerycznych agentów (workerów) jako osobne pody, co jeszcze bardziej redukuje koszty i Toil.

Pomocne linki:

- https://cloud.google.com/compute/docs/access/service-accounts
- https://plugins.jenkins.io/google-compute-engine/

Analiza i Podsumowanie (GCP DevOps Expert)

Wybór między Compute Engine a GKE dla Jenkinsa zależy od skali. Dla prostych wdrożeń VM (GCE) jest wystarczający, dla dużej skali GKE wygrywa dzięki elastyczności agentów.

💡 Kluczowe wnioski:

  • Least Privilege: Jenkins powinien mieć przypisane konto serwisowe tylko z takimi uprawnieniami, jakich faktycznie potrzebuje do wdrożenia aplikacji (np. `roles/storage.admin` dla GCS lub `roles/container.developer` dla GKE).
  • Immutable Master: Staraj się konfigurować Jenkinsa "jako kod" (CasC - Configuration as Code), aby móc go łatwo odtworzyć na nowej maszynie VM.
  • Ephemeral Workers: Najlepszą metodą na "Operational Toil" jest sprawienie, by agenci Jenkinsa żyli tylko na czas budowania (np. używając wtyczki Google Compute Engine do dynamicznego startowania VM-ów).

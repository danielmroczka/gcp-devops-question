Question 20 / 201

You support an application deployed on Compute Engine. The application connects to a Cloud SQL instance to store and retrieve data. After an update to the application, users report errors showing database timeout messages. The number of concurrent active users remained stable. You need to find the most probable cause of the database timeout. What should you do?

  • A. Check the serial port logs of the Compute Engine instance.
  • B. Use Stackdriver Profiler to visualize the resources utilization throughout the application.
  • C. Determine whether there is an increased number of connections to the Cloud SQL instance.
  • D. Use Cloud Security Scanner to see whether your Cloud SQL is under a Distributed Denial of Service (DDoS) attack.
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Gdy aplikacja zaczyna zwracać błędy typu "database timeout" po aktualizacji, a liczba użytkowników jest stabilna, najczęstszą przyczyną są problemy z pulą połączeń (connection pooling) lub wycieki połączeń w nowym kodzie. Sprawdzenie liczby aktywnych połączeń do Cloud SQL pozwala ustalić, czy aplikacja nie otwiera ich zbyt wiele, wyczerpując dostępny limit Cloud SQL.

A. Logi portu szeregowego pomagają przy awariach systemu operacyjnego, nie przy timeoutach aplikacji do bazy danych.
B. Stackdriver Profiler (Cloud Profiler) jest doskonały do badania wydajności CPU i pamięci wewnątrz kodu aplikacji, ale problem dotyczy specyficznie połączenia z bazą danych (timeouty), a nie ogólnego wykorzystania zasobów (CPU/RAM).
D. Cloud Security Scanner skanuje luki bezpieczeństwa (np. XSS), nie służy do badania wydajności bazy danych ani przyczyn timeoutów.

Analiza i Podsumowanie Dyskusji (AI)

W DevOps: Timeouty do bazy = Najpierw sprawdź metrykę "Connections". To najszybszy sposób na potwierdzenie problemów z pulą połączeń.

💡 Wskazówki i Triki (Exam Tips)

  • Timeout do bazy? Szukaj liczby aktywnych połączeń (Connections) w metrykach bazy.

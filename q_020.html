Question 20 / 201

You support an application deployed on Compute Engine. The application connects to a Cloud SQL instance to store and retrieve data. After an update to the application, users report errors showing database timeout messages. The number of concurrent active users remained stable. You need to find the most probable cause of the database timeout.

What should you do?

  • A. Check the serial port logs of the Compute Engine instance.
  • B. Use Stackdriver Profiler to visualize the resources utilization throughout the application.
  • C. Determine whether there is an increased number of connections to the Cloud SQL instance.
  • D. Use Cloud Security Scanner to see whether your Cloud SQL is under a Distributed Denial of Service (DDoS) attack.
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Poprawną odpowiedzią jest **C (Determine whether there is an increased number of connections to the Cloud SQL instance)**.

**Dlaczego C jest poprawne?**
Gdy aplikacja zgłasza błędy typu "timeout" przy połączeniu z bazą danych po aktualizacji kodu, a liczba użytkowników pozostaje bez zmian, najczęstszym winowajcą jest niewłaściwe zarządzanie połączeniami (connection management). Nowa wersja aplikacji może zawierać błąd powodujący tzw. wyciek połączeń (connection leak) – sytuację, w której połączenia z bazą są otwierane, ale nie są zamykane i zwracane do puli. Cloud SQL ma limity jednoczesnych połączeń; po ich wyczerpaniu każda kolejna próba połączenia zakończy się timeoutem. Sprawdzenie metryk połączeń w Cloud Monitoring jest najszybszym sposobem na potwierdzenie tej hipotezy.

**Dlaczego pozostałe opcje są błędne?**
*   **A. Check the serial port logs of the Compute Engine instance:** Logi portu szeregowego są niezwykle przydatne do diagnozowania problemów z uruchamianiem systemu operacyjnego (boot issues), błędów kernela lub problemów z siecią na poziomie systemu VM. Nie dostarczają one jednak informacji o logice aplikacji ani o jej interakcji z zewnętrzną bazą danych Cloud SQL.
*   **B. Use Stackdriver Profiler to visualize the resources utilization throughout the application:** Cloud Profiler służy do analizy zużycia procesora (CPU) i pamięci przez poszczególne funkcje w kodzie aplikacji. Choć może pomóc znaleźć nieefektywny kod, błąd "database timeout" jest specyficzny dla warstwy komunikacji z bazą. Profiler nie pokaże bezpośrednio problemu z wyczerpaniem puli połączeń w Cloud SQL.
*   **D. Use Cloud Security Scanner to see whether your Cloud SQL is under a Distributed Denial of Service (DDoS) attack:** Cloud Security Scanner to narzędzie do wykrywania luk w zabezpieczeniach (np. XSS, niebezpieczne biblioteki). Nie służy ono do monitorowania ruchu sieciowego pod kątem ataków DDoS ani do analizy wydajności bazy danych. Do ochrony przed DDoS w GCP służy usługa **Google Cloud Armor**.

### 💡 Hity i triki (Hints & Tricks)
- Scenariusz: **Aktualizacja kodu + błędy bazy + stały ruch = Wyciek połączeń (Connection Leak)**.
- Zawsze sprawdzaj metryki Cloud SQL: `database/instance/connections` to Twój pierwszy punkt styku przy diagnozowaniu timeoutów.
- Pamiętaj, że limity połączeń w Cloud SQL zależą od rozmiaru instancji (liczby vCPU i RAM).

Analiza i Podsumowanie (AI)

Pytanie to symuluje realny incydent produkcyjny typu "regression". Kluczem jest umiejętność odróżnienia problemów z zasobami obliczeniowymi (CPU/RAM) od problemów z zasobami zewnętrznymi (Database connections).

Kluczowe punkty:

  • Root Cause Analysis (RCA): Izolacja zmiany (aktualizacja kodu) jako głównej przyczyny problemu.
  • Connection Pooling: Zrozumienie, jak aplikacje zarządzają sesjami bazy danych.
  • Metric-Driven Development: Wykorzystanie Cloud Monitoring do szybkiej weryfikacji stanu infrastruktury.

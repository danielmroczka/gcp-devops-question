Question 54 / 201

Stackdriver

You are using Stackdriver to monitor applications hosted on Google Cloud Platform (GCP). You recently deployed a new application, but its logs are not appearing on the Stackdriver dashboard. You need to troubleshoot the issue. What should you do?

  • A. Confirm that the Stackdriver agent has been installed in the hosting virtual machine.
  • B. Confirm that your account has the proper permissions to use the Stackdriver dashboard.
  • C. Confirm that port 25 has been opened in the firewall to allow messages through to Stackdriver.
  • D. Confirm that the application is using the required client library and the service account key has proper permissions.
Show Suggested Answer
Suggested Answer: A 
Poprawna odpowiedź: A. Confirm that the Stackdriver agent has been installed in the hosting virtual machine.

Wyjaśnienie:
W środowisku Google Compute Engine (GCE), logi systemowe i niektóre podstawowe metryki są zbierane automatycznie, ale logi aplikacji (np. te zapisywane do plików w /var/log/...) wymagają zainstalowania i skonfigurowania agenta (dawniej Stackdriver Logging Agent, obecnie Ops Agent). Bez tego agenta Cloud Logging nie "widzi" tego, co dzieje się wewnątrz systemu operacyjnego maszyny wirtualnej.

Dlaczego inne odpowiedzi są błędne:
- B: Proper permissions for the dashboard: Uprawnienia do dashboardu pozwalają na przeglądanie danych, które już są w systemie. Gdyby to był problem z uprawnieniami użytkownika, logi wciąż byłyby widoczne w Log Explorerze dla kogoś z rolą Logging Admin, a pytanie sugeruje, że logi w ogóle nie trafiają do Stackdrivera.
- C: Port 25: Port 25 jest używany dla protokołu SMTP (poczta elektroniczna). Przesyłanie logów do Google Cloud API odbywa się drogą bezpieczną przez HTTPS na porcie 443. Otwieranie portu 25 nie ma żadnego związku z logowaniem.
- D: Client library and service account key: Choć użycie bibliotek klienckich jest jedną z metod wysyłania logów, standardową i zalecaną praktyką dla aplikacji na VM jest logowanie do stdout/stderr lub plików, które są następnie przechwytywane przez agenta. Co więcej, używanie "kluczy konta serwisowego" (service account keys) wewnątrz GCP jest odradzane na rzecz domyślnych kont serwisowych instancji (Application Default Credentials).

Hity i triki (GCP DevOps Exam):
- Jeśli pytanie dotyczy braku logów z Compute Engine (VM) -> Zawsze najpierw sprawdź, czy zainstalowany jest Ops Agent (lub stary Logging Agent).
- Pamiętaj o rolach IAM dla instancji: Nawet z agentem, VM musi mieć przypisane konto serwisowe z rolą `roles/logging.logWriter`, aby móc wysyłać logi.
- Cloud Logging obsługuje automatycznie GKE (standard output) i App Engine. VM-y to jedyne miejsce, gdzie agent jest krytyczny dla logów aplikacyjnych.

- https://cloud.google.com/logging/docs/access-control
- https://cloud.google.com/compute/docs/access/service-accounts

Analiza i Podsumowanie (GCP DevOps Expert)

Kwestia zbierania logów w GCP zależy od typu usługi (PaaS vs IaaS). W przypadku IaaS (Compute Engine), odpowiedzialność za przekazywanie logów z wnętrza systemu operacyjnego leży po stronie użytkownika, co realizuje się poprzez instalację agenta.

💡 Kluczowe wnioski:

  • Ops Agent: To obecnie standardowy agent dla Compute Engine, łączący funkcje Logging i Monitoring.
  • IAM Roles: Bez roli roles/logging.logWriter logi nigdy nie trafią do systemu, nawet jeśli agent działa poprawnie.
  • Standard Streams: Najlepszą praktyką w nowoczesnych aplikacjach (Cloud Native) jest wypisywanie logów na stdout i stderr.

Question 6 / 201

Cloud Build GKE Kubernetes Monitoring

You use a multiple step Cloud Build pipeline to build and deploy your application to Google Kubernetes Engine (GKE). You want to integrate with a third-party monitoring platform by performing a HTTP POST of the build information to a webhook. You want to minimize the development effort.

What should you do?

  • A. Add logic to each Cloud Build step to HTTP POST the build information to a webhook.
  • B. Add a new step at the end of the pipeline in Cloud Build to HTTP POST the build information to a webhook.
  • C. Use Stackdriver Logging to create a logs-based metric from the Cloud Build logs. Create an Alert with a Webhook notification type.
  • D. Create a Cloud Pub/Sub push subscription to the Cloud Build cloud-builds PubSub topic to HTTP POST the build information to a webhook.
Show Suggested Answer
Suggested Answer: D 
Odpowiedź: D.

Wyjaśnienie:
Najbardziej efektywnym i najmniej pracochłonnym sposobem integracji Cloud Build z zewnętrznymi systemami jest wykorzystanie natywnego mechanizmu powiadomień opartego na usłudze Cloud Pub/Sub. 

Dlaczego odpowiedź D jest poprawna:
Cloud Build automatycznie publikuje wiadomości o stanie każdego buildu (np. `QUEUED`, `WORKING`, `SUCCESS`, `FAILURE`) na dedykowany temat (topic) Pub/Sub o nazwie `cloud-builds`. Utworzenie subskrypcji typu "Push" na tym temacie pozwala na automatyczne wysyłanie tych informacji pod wskazany adres URL (webhook) zewnętrznej platformy monitorującej. Jest to rozwiązanie "event-driven", które nie wymaga modyfikacji kodu aplikacji ani konfiguracji samego pliku `cloudbuild.yaml`.

Dlaczego pozostałe opcje są błędne:
A. Dodawanie logiki do każdego kroku builda jest czasochłonne, trudne w utrzymaniu i zwiększa ryzyko błędów. Każda zmiana w procesie budowania wymagałaby aktualizacji wielu kroków.
B. Dodanie kroku na końcu pipeline'u (np. wykonującego `curl` do webhooka) jest lepsze niż opcja A, ale wciąż wymaga modyfikacji pliku konfiguracyjnego buildu. Dodatkowo, jeśli którykolwiek z wcześniejszych kroków zawiedzie, ostatni krok może się nie wykonać (chyba że zostanie jawnie skonfigurowany jako `allowFailure` lub użyjemy niestandardowej logiki), co spowoduje brak powiadomienia o błędzie.
C. Używanie metryk opartych na logach (logs-based metrics) i alertów Cloud Monitoring jest przekomplikowane w tym scenariuszu. Alerty są przeznaczone do powiadamiania o incydentach, a nie do systematycznego przesyłania danych o każdym zakończonym buildzie do zewnętrznych platform.

Hity i triki:
- Zapamiętaj: Cloud Build + powiadomienia zewnętrzne = Pub/Sub topic `cloud-builds`.
- Subskrypcja "Push" w Pub/Sub to najprostszy sposób na integrację z webhookami bez pisania dodatkowego kodu (np. Cloud Functions).
- Możesz filtrować wiadomości w Pub/Sub, aby wysyłać do webhooka tylko informacje o buildach, które zakończyły się błędem (`FAILURE`).

Przydatne linki:
- https://cloud.google.com/build/docs/subscribe-build-notifications
- https://cloud.google.com/pubsub/docs/push

Analiza i Podsumowanie Dyskusji (AI)

Kluczem do rozwiązania tego pytania jest zrozumienie architektury sterowanej zdarzeniami (event-driven) w Google Cloud. Pub/Sub służy jako centralna szyna informacyjna dla usług GCP.

💡 Wskazówki i Triki (Exam Tips)

  • Minimalizacja wysiłku (Minimize effort): Szukaj rozwiązań natywnych, które nie wymagają pisania kodu lub dużej zmiany konfiguracji.
  • Automatyczne tematy: Niektóre usługi GCP (jak Cloud Build) mają predefiniowane tematy Pub/Sub, które wystarczy zasubskrybować.
  • Webhooks: Jeśli celem jest HTTP POST do zewnętrznego systemu, Pub/Sub Push Subscription jest prawie zawsze poprawną odpowiedzią.

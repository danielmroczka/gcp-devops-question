Question 8 / 201

SLI

You support a high-traffic web application and want to ensure that the home page loads in a timely manner. As a first step, you decide to implement a Service Level Indicator (SLI) to represent home page request latency with an acceptable page load time set to 100 ms.

What is the Google-recommended way of calculating this SLI?

  • A. Bucketize the request latencies into ranges, and then compute the percentile at 100 ms.
  • B. Bucketize the request latencies into ranges, and then compute the median and 90th percentiles.
  • C. Count the number of home page requests that load in under 100 ms, and then divide by the total number of home page requests.
  • D. Count the number of home page request that load in under 100 ms, and then divide by the total number of all web application requests.
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Zgodnie z praktykami Site Reliability Engineering (SRE) promowanymi przez Google, wskaźniki SLI (Service Level Indicators) powinny być wyrażone jako stosunek liczby zdarzeń spełniających określone kryterium ("dobrych") do całkowitej liczby istotnych zdarzeń.

Dlaczego odpowiedź C jest poprawna:
Dla latencji (opóźnienia) celem jest zazwyczaj utrzymanie czasu ładowania poniżej pewnego progu (w tym przypadku 100 ms). Najbardziej miarodajnym sposobem obliczenia SLI jest zliczenie wszystkich żądań do strony głównej, których czas odpowiedzi był krótszy niż 100 ms, a następnie podzielenie tej liczby przez całkowitą liczbę żądań skierowanych do tej konkretnej strony głównej. Wynik (zazwyczaj w procentach) bezpośrednio informuje, jak często udaje się spełnić oczekiwania użytkownika.

Dlaczego pozostałe opcje są błędne:
A. Kubułkowanie (bucketization) latencji i obliczanie percentyli jest przydatne do wizualizacji rozkładu i zrozumienia zachowania "ogona" latencji (np. P99), ale same w sobie nie stanowią SLI w formacie rekomendowanym do budowania budżetów błędów (Error Budgets). SLI musi być formatem "zdał/nie zdał".
B. Mediana (P50) i 90-ty percentyl dają dobry obraz ogólnej wydajności, ale podobnie jak opcja A, nie pozwalają na łatwe obliczenie budżetu błędów dla konkretnego progu 100 ms.
D. Dzielenie liczby szybkich żądań do strony głównej przez liczbę *wszystkich* żądań do całej aplikacji jest błędem metodologicznym. Każdy endpoint (strona główna, koszyk, API wyszukiwania) może mieć inne cele latencji (np. API może być szybsze niż renderowanie HTML). Mieszanie tych danych sprawiłoby, że wskaźnik stałby się nieczytelny i bezużyteczny do monitorowania konkretnej strony głównej.

Hity i triki:
- Formuła na SLI: (Dobre zdarzenia / Wszystkie ważne zdarzenia) * 100%.
- Zapamiętaj: SLI to wskaźnik (liczba), SLO to cel (np. 99.9% sukcesów), SLA to umowa prawna.
- Wybierając mianownik (denominator), zawsze upewnij się, że zawiera on tylko te zdarzenia, które są istotne dla danego wskaźnika.

Analiza i Podsumowanie Dyskusji (AI)

Wskaźniki oparte na proporcjach (ratio-based SLIs) są fundamentem SRE, ponieważ bezpośrednio przekładają się na Error Budgets – kluczowe narzędzie do zarządzania ryzykiem i prędkością wdrażania zmian.

💡 Wskazówki i Triki (Exam Tips)

  • SLI = Ratio: Jeśli pytanie dotyczy rekomendowanego sposobu obliczania SLI, szukaj opcji, która dzieli "dobre" przez "wszystkie".
  • Scope (Zakres): Upewnij się, że licznik i mianownik dotyczą tego samego zestawu danych (np. ta sama strona, ten sam typ żądań).
  • Latency Threshold: SLI latencji to nie jest "średnia latencja", ale "% żądań poniżej X ms".

Question 38 / 201

Logging Stackdriver

You are running an application on Compute Engine and collecting logs through Stackdriver. You discover that some personally identifiable information (PII) is leaking into certain log entry fields. All PII entries begin with the text userinfo. You want to capture these log entries in a secure location for later review and prevent them from leaking to Stackdriver Logging.

What should you do?

  • A. Create a basic log filter matching userinfo, and then configure a log export in the Stackdriver console with Cloud Storage as a sink.
  • B. Use a Fluentd filter plugin with the Stackdriver Agent to remove log entries containing userinfo, and then copy the entries to a Cloud Storage bucket.
  • C. Create an advanced log filter matching userinfo, configure a log export in the Stackdriver console with Cloud Storage as a sink, and then configure a log exclusion with userinfo as a filter.
  • D. Use a Fluentd filter plugin with the Stackdriver Agent to remove log entries containing userinfo, create an advanced log filter matching userinfo, and then configure a log export in the Stackdriver console with Cloud Storage as a sink.
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Poprawna odpowiedź to C. W Google Cloud Logging najbardziej efektywnym i natywnym sposobem na obsługę logów zawierających wrażliwe dane (PII) jest połączenie mechanizmu **Zlewów (Sinks/Exports)** oraz **Wykluczeń (Exclusions)**.
1. **Eksport (Sink):** Pozwala na przekierowanie logów pasujących do filtra (np. `userinfo`) do bezpiecznego miejsca, takiego jak Cloud Storage, gdzie dostęp jest ściśle kontrolowany. Ważne: Sinki przetwarzają logi *zanim* zostaną one odrzucone przez filtry wykluczające.
2. **Wykluczenie (Exclusion):** Pozwala na odrzucenie logów pasujących do filtra, aby nie były one zapisywane (ingested) w standardowych zasobnikach Cloud Logging (`_Default`, `_Required`). Dzięki temu dane PII nie są widoczne w Logs Explorerze i nie generują kosztów przechowywania w systemie logowania.

Dlaczego inne odpowiedzi są błędne:
A. Sam eksport (Sink) bez wykluczenia (Exclusion) spowoduje, że logi trafią do Cloud Storage, ale NADAL zostaną zapisane w Cloud Logging, co oznacza, że dane PII "wyciekną" do ogólnodostępnych dzienników systemowych.
B. Filtrowanie na poziomie agenta (Fluentd) i ręczne kopiowanie do GCS jest skomplikowane ("Toil") i trudne do utrzymania w dużej skali. Wymagałoby to instalacji dodatkowych wtyczek i zarządzania poświadczeniami na każdej maszynie VM.
D. Jeśli usuniesz (remove) logi za pomocą Fluentd, nigdy nie trafią one do usługi Cloud Logging, więc nie będzie możliwe ich wyeksportowanie za pomocą konfiguracji "log export" w konsoli GCP.

Hity i triki (Exam Tips):
- **Sinks vs Exclusions:** Zapamiętaj tę parę. Sinks "kopiują" logi do innego miejsca, Exclusions "zatrzymują" logi przed zapisaniem w Cloud Logging. Sinki działają PIERWSZE.
- **PII w logach:** Zawsze szukaj rozwiązania, które usuwa te dane z widoku ogólnego (Logs Explorer) i przenosi je do bezpiecznego archiwum (GCS/BigQuery).
- **Koszty:** Wykluczenia są świetnym sposobem na redukcję kosztów Cloud Logging przy zachowaniu logów w tańszym Cloud Storage.

Analiza i Podsumowanie Dyskusji (AI)

Zarządzanie danymi wrażliwymi w logach to krytyczny aspekt zgodności (compliance). Architektura GCP pozwala na elastyczne sterowanie przepływem logów, co umożliwia realizację złożonych wymagań bezpieczeństwa bez wpływu na wydajność aplikacji.

💡 Wskazówki i Triki (Exam Tips)

  • Data Masking: Dla bardzo wrażliwych danych rozważ użycie Cloud DLP (Data Loss Prevention) do automatycznego maskowania PII przed ich zapisaniem.
  • Centralized Logging: W dużych organizacjach sinki i wykluczenia konfiguruje się na poziomie folderu lub całej organizacji, aby zapewnić spójne polityki bezpieczeństwa.
  • Audit Logs: Pamiętaj, że logi audytowe (`_Required`) nie mogą być wykluczone ani usunięte.

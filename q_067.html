Question 67 / 201

GKE Kubernetes

Your company is developing applications that are deployed on Google Kubernetes Engine (GKE). Each team manages a different application. You need to create the development and production environments for each team, while minimizing costs. Different teams should not be able to access other teams' environments.

What should you do?

  • A. Create one GCP Project per team. In each project, create a cluster for Development and one for Production. Grant the teams IAM access to their respective clusters.
  • B. Create one GCP Project per team. In each project, create a cluster with a Kubernetes namespace for Development and one for Production. Grant the teams IAM access to their respective clusters.
  • C. Create a Development and a Production GKE cluster in separate projects. In each cluster, create a Kubernetes namespace per team, and then configure Identity Aware Proxy so that each team can only access its own namespace.
  • D. Create a Development and a Production GKE cluster in separate projects. In each cluster, create a Kubernetes namespace per team, and then configure Kubernetes Role-based access control (RBAC) so that each team can only access its own namespace.
Show Suggested Answer
Suggested Answer: D 
Odpowiedź: D.

Wyjaśnienie:
Poprawna odpowiedź to D. Strategia ta idealnie balansuje trzy kluczowe wymagania: izolację zespołów, separację środowisk (Dev/Prod) oraz minimalizację kosztów.

Dlaczego odpowiedź D jest poprawna:
1. Separacja środowisk (Dev vs Prod): Użycie osobnych klastrów (i projektów) dla Developmentu i Produkcji to "best practice" w zakresie bezpieczeństwa i niezawodności. Zapobiega to przypadkowym zmianom na produkcji podczas prac deweloperskich (ograniczenie "Blast Radius").
2. Minimalizacja kosztów (Multi-tenancy): Zamiast tworzyć osobne klastry dla każdego zespołu (co byłoby bardzo drogie ze względu na narzut płaszczyzny sterowania i mniejszą utylizację węzłów), tworzymy współdzielone klastry. Zespoły dzielą zasoby obliczeniowe wewnątrz klastra, co jest znacznie tańsze.
3. Izolacja zespołów: Kubernetes Namespaces (przestrzenie nazw) w połączeniu z Kubernetes RBAC (Role-Based Access Control) pozwalają na precyzyjne ograniczenie uprawnień deweloperów tylko do ich własnych obszarów roboczych.

Analiza błędnych odpowiedzi:
- A: Tworzenie dwóch klastrów na każdy zespół (np. 10 zespołów = 20 klastrów) jest niezwykle nieefektywne kosztowo. Płacisz za każdy klaster (Management Fee) i tracisz korzyści z "bin-packingu" (współdzielenia węzłów).
- B: Podobnie jak w punkcie A, tworzenie osobnego projektu i klastra na każdy zespół generuje ogromne koszty i narzut administracyjny ("Toil").
- C: Identity Aware Proxy (IAP) służy do uwierzytelniania użytkowników próbujących uzyskać dostęp do aplikacji internetowych (HTTP) bez konieczności korzystania z VPN. Nie jest to narzędzie do zarządzania uprawnieniami wewnątrz klastra Kubernetes ani do izolacji przestrzeni nazw.

Hity i triki (Exam Tips):
- Słowo klucz "Minimize costs" w kontekście GKE zazwyczaj sugeruje współdzielenie klastra (Namespaces).
- Słowo klucz "Team isolation" sugeruje RBAC lub Network Policies.
- Pamiętaj o różnicy: IAM zarządza dostępem do **GCP Resources** (cały klaster), natomiast RBAC zarządza dostępem do **Kubernetes Resources** (np. konkretny Namespace).

Analiza i Podsumowanie Dyskusji (AI)

W projektowaniu infrastruktury GKE kluczowe jest rozróżnienie między "Soft Multi-tenancy" (izolacja za pomocą Namespaces) a "Hard Multi-tenancy" (izolacja za pomocą osobnych klastrów). Odpowiedź D łączy oba te podejścia, oferując twardą izolację między światem deweloperskim a produkcyjnym oraz miękką izolację między poszczególnymi zespołami projektowymi.

💡 Wskazówki i Triki (Exam Tips)

  • Zawsze oddzielaj Produkcję od Developmentu na poziomie Projektu GCP – to standardowa bariera bezpieczeństwa.
  • Namespaces nie zapewniają pełnej izolacji sieciowej domyślnie. W rzeczywistym środowisku (i czasami na egzaminie) należy wspomnieć o **Network Policies**, aby zablokować ruch między przestrzeniami nazw.
  • Wykorzystuj GKE Autopilot, jeśli minimalizacja kosztów i narzutu administracyjnego jest absolutnym priorytetem (choć w pytaniach o architekturę często zakłada się Standard).

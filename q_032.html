Question 32 / 201

You support a production service that runs on a single Compute Engine instance. You regularly need to spend time on recreating the service by deleting the crashing instance and creating a new instance based on the relevant image. You want to reduce the time spent performing manual operations while following Site Reliability Engineering principles.

What should you do?

  • A. File a bug with the development team so they can find the root cause of the crashing instance.
  • B. Create a Managed instance Group with a single instance and use health checks to determine the system status.
  • C. Add a Load Balancer in front of the Compute Engine instance and use health checks to determine the system status.
  • D. Create a Stackdriver Monitoring dashboard with SMS alerts to be able to start recreating the crashed instance promptly after it was crashed.
Show Suggested Answer
Suggested Answer: B 
Odpowiedź: B.

Wyjaśnienie:
Poprawna odpowiedź to B. Zgodnie z zasadami SRE (Site Reliability Engineering), kluczowym celem jest eliminacja "Toil" – czyli powtarzalnej, manualnej pracy, która nie wnosi trwałej wartości. Ręczne usuwanie i tworzenie nowej instancji Compute Engine po awarii jest klasycznym przykładem Toil. Rozwiązaniem jest użycie Managed Instance Group (MIG) z włączoną funkcją **auto-healing**. Dzięki health checkom system automatycznie wykrywa awarię aplikacji i bez udziału inżyniera dokonuje rekreacji (recreate) uszkodzonej instancji, zapewniając ciągłość działania usługi.

Dlaczego inne odpowiedzi są błędne:
A. Zgłoszenie błędu (RCA - Root Cause Analysis) jest ważne dla długofalowej stabilności, ale nie rozwiązuje bieżącego problemu manualnego nakładu pracy (Toil) przy przywracaniu usługi.
C. Load Balancer (LB) potrafi jedynie przekierować ruch na inne (zdrowe) instancje. Jeśli masz tylko jedną instancję i ona padnie, LB po prostu zgłosi błąd 5xx, ale nie naprawi samej maszyny wirtualnej.
D. Alerty SMS jedynie skracają czas reakcji (Mean Time to Detect), ale proces naprawy wciąż pozostaje manualny. SRE dąży do tego, by system naprawiał się sam, a inżynier był informowany o tym fakcie po czasie (jeśli w ogóle).

Hity i triki (Exam Tips):
- Słowa klucze: "manual operations", "Toil", "SRE" -> szukaj **automatyzacji** (Auto-healing, Autoscaling, CI/CD).
- Nawet jeśli usługa nie wymaga skalowania (zawsze 1 instancja), użycie MIG jest zalecane ze względu na darmowy mechanizm automatycznej naprawy.
- Pamiętaj o zasadzie: "Self-healing infrastructure is a core DevOps/SRE capability".

Analiza i Podsumowanie Dyskusji (AI)

Eliminacja Toil to nie tylko wygoda dla inżynierów, to przede wszystkim szybkość naprawy (MTTR). Automat zawsze zareaguje szybciej niż człowiek budzony w nocy przez SMS.

💡 Wskazówki i Triki (Exam Tips)

  • Auto-healing Configuration: Pamiętaj, że do działania auto-healingu potrzebujesz: 1. Health Checka, 2. Instance Template, 3. Managed Instance Group.
  • Grace Period: Przy konfiguracji auto-healingu ustaw odpowiedni "initial delay", aby dać instancji czas na uruchomienie aplikacji przed pierwszą kontrolą zdrowia.
  • SRE mindset: Jeśli coś musisz zrobić ręcznie więcej niż dwa razy – zautomatyzuj to.

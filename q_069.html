Question 69 / 201

You manage several production systems that run on Compute Engine in the same Google Cloud Platform (GCP) project. Each system has its own set of dedicated Compute Engine instances. You want to know how must it costs to run each of the systems.

What should you do?

  • A. In the Google Cloud Platform Console, use the Cost Breakdown section to visualize the costs per system.
  • B. Assign all instances a label specific to the system they run. Configure BigQuery billing export and query costs per label.
  • C. Enrich all instances with metadata specific to the system they run. Configure Stackdriver Logging to export to BigQuery, and query costs based on the metadata.
  • D. Name each virtual machine (VM) after the system it runs. Set up a usage report export to a Cloud Storage bucket. Configure the bucket as a source in BigQuery to query costs based on VM name.
Show Suggested Answer
Suggested Answer: B 
Odpowiedź: B.

Wyjaśnienie:
Poprawna odpowiedź to B. Zarządzanie kosztami (FinOps) w chmurze wymaga precyzyjnego oznaczania zasobów, aby móc przypisać wydatki do konkretnych jednostek biznesowych lub systemów.

Dlaczego odpowiedź B jest poprawna:
1. Etykiety (Labels): To standardowy mechanizm w GCP do kategoryzacji zasobów. Są to pary klucz-wartość, które są natywnie wspierane przez system billingowy. Możesz nadać instancjom etykietę np. `system:ordering` lub `system:payment`.
2. Billing Export do BigQuery: Jest to najpotężniejsze narzędzie do analizy kosztów w GCP. Po włączeniu eksportu, wszystkie dane o kosztach trafiają do BigQuery wraz z przypisanymi do zasobów etykietami. Pozwala to na pisanie zapytań SQL, które precyzyjnie sumują koszty dla każdej etykiety.
3. Skalowalność i precyzja: To rozwiązanie działa automatycznie dla wszystkich instancji i pozwala na tworzenie zaawansowanych dashboardów (np. w Looker Studio).

Analiza błędnych odpowiedzi:
- A: "Cost Breakdown" w konsoli GCP jest przydatne do ogólnego przeglądu (np. kosztów per usługa jak Compute Engine vs Cloud Storage), ale bez użycia etykiet nie pozwoli na rozróżnienie kosztów poszczególnych systemów działających w ramach tego samego projektu.
- C: Metadane instancji służą do konfiguracji wewnątrz systemu operacyjnego (np. skrypty startowe, klucze SSH). Nie są one przekazywane do systemu bilingowego. Cloud Logging (dawniej Stackdriver) służy do monitorowania i logowania zdarzeń, a nie do analizy finansowej.
- D: Raporty użycia (Usage reports) w Cloud Storage są mniej elastyczne i trudniejsze w analizie niż natywny eksport bilingowy do BigQuery. Poleganie na nazwach VM (naming convention) jest ryzykowne, ponieważ nazwy mogą być niespójne, a system bilingowy GCP promuje etykiety jako oficjalny standard raportowania.

Hity i triki (Exam Tips):
- **Labels vs Tags**: Zapamiętaj tę różnicę! **Labels** służą do bilingu i organizacji zasobów. **Tags** (network tags) służą wyłącznie do reguł firewalli i routingu. To częsta pułapka na egzaminie.
- Etykiety są propagowane (dziedziczone) w dół w niektórych usługach, ale w Compute Engine musisz je nadać bezpośrednio instancjom lub szablonon instancji (Instance Templates).
- Jeśli widzisz pytanie o "granulację kosztów" lub "podział kosztów per dział/system" – szukaj "Labels" i "BigQuery Export".

Analiza i Podsumowanie Dyskusji (AI)

W kontekście DevOps i SRE, zrozumienie kosztów (Cost Observability) jest równie ważne jak monitorowanie wydajności. Podejście "Label everything" pozwala na wdrożenie kultury odpowiedzialności za koszty w zespołach deweloperskich (Cloud Financial Management).

💡 Wskazówki i Triki (Exam Tips)

  • W dużych organizacjach warto wymuszać stosowanie etykiet za pomocą **Organization Policy** lub skryptów automatyzacji (np. Terraform).
  • Eksport bilingowy do BigQuery zawiera również informacje o rabatach (CUDs - Committed Use Discounts) oraz kredytach, co pozwala na wyliczenie realnego kosztu netto (amortyzowanego).
  • Używaj etykiet do automatyzacji – np. skryptów, które wyłączają na noc wszystkie instancje z etykietą `env:dev`.

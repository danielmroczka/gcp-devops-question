Question 31 / 201

GKE Kubernetes Monitoring

Your team is designing a new application for deployment into Google Kubernetes Engine (GKE). You need to set up monitoring to collect and aggregate various application-level metrics in a centralized location. You want to use Google Cloud Platform services while minimizing the amount of work required to set up monitoring.

What should you do?

  • A. Publish various metrics from the application directly to the Stackdriver Monitoring API, and then observe these custom metrics in Stackdriver.
  • B. Install the Cloud Pub/Sub client libraries, push various metrics from the application to various topics, and then observe the aggregated metrics in Stackdriver.
  • C. Install the OpenTelemetry client libraries in the application, configure Stackdriver as the export destination for the metrics, and then observe the application's metrics in Stackdriver.
  • D. Emit all metrics in the form of application-specific log messages, pass these messages from the containers to the Stackdriver logging collector, and then observe metrics in Stackdriver.
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Poprawna odpowiedź to C. OpenTelemetry (OTel) jest obecnie standardem branżowym dla metryk, logów i śledzenia (observability) w środowiskach chmurowych i kontenerowych. Jest to rozwiązanie rekomendowane przez Google Cloud, które minimalizuje nakład pracy (Toil) dzięki gotowym bibliotekom klienckim i eksporterom do Google Cloud Monitoring (dawniej Stackdriver). Deweloperzy mogą skupić się na definiowaniu metryk, a nie na implementowaniu logiki komunikacji z API.

Dlaczego inne odpowiedzi są błędne:
A. Bezpośrednie korzystanie z API Cloud Monitoring jest możliwe, ale wymaga pisania i utrzymywania własnego kodu do obsługi połączeń, uwierzytelniania i formatowania danych. Jest to podejście typu "manual plumbing", które generuje zbędny nakład pracy.
B. Cloud Pub/Sub jest systemem kolejkowym do asynchronicznej komunikacji między serwisami. Używanie go jako pośrednika dla metryk jest nadmiarowe, skomplikowane i nie oferuje natywnej agregacji metryk w systemie monitoringu.
D. Przesyłanie metryk w formie logów (log-based metrics) jest nieefektywne i kosztowne. Logi są znacznie droższe w przechowywaniu i przetwarzaniu niż metryki typu time-series, a ich agregacja wymaga dodatkowej konfiguracji (sinki, parsery).

Hity i triki (Exam Tips):
- Jeśli pytanie dotyczy zbierania metryk w nowoczesnej aplikacji (GKE, Microservices) i minimalizacji pracy -> szukaj **OpenTelemetry** lub **Managed Service for Prometheus**.
- OpenTelemetry zapewnia brak "vendor lock-in" – możesz łatwo wysłać te same metryki do GCP, Datadog czy własnego Prometheusa.
- Pamiętaj o różnicy kosztów: Metryki są tańsze niż Logi. Zawsze preferuj metryki dla danych numerycznych.

Dokumentacja:
- https://cloud.google.com/stackdriver/docs/managed-prometheus
- https://opentelemetry.io/docs/concepts/observability-primer/

Analiza i Podsumowanie Dyskusji (AI)

Kierunek rozwoju monitoringu w Google Cloud wyraźnie zmierza w stronę otwartych standardów. OpenTelemetry zastąpiło starsze biblioteki (jak OpenCensus), stając się fundamentem dla "Observability" w nowoczesnych systemach.

💡 Wskazówki i Triki (Exam Tips)

  • Managed Service for Prometheus: To kolejna ważna usługa w GKE. Jeśli Twoja aplikacja już używa formatu Prometheus, to jest to najprostsza metoda bez zmiany kodu.
  • Custom Metrics: Pamiętaj, że metryki wysyłane przez OTel trafiają do Cloud Monitoring jako "Custom Metrics", co może wiązać się z kosztami przy dużej liczbie etykiet (high cardinality).
  • Toil: SRE zawsze dąży do redukcji pracy manualnej. Standardowe biblioteki (OTel) to mniej kodu do utrzymania przez Twój zespół.

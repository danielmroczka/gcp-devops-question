Question 55 / 201

Your organization recently adopted a container-based workflow for application development. Your team develops numerous applications that are deployed continuously through an automated build pipeline to the production environment. A recent security audit alerted your team that the code pushed to production could contain vulnerabilities and that the existing tooling around virtual machine (VM) vulnerabilities no longer applies to the containerized environment. You need to ensure the security and patch level of all code running through the pipeline.

What should you do?

  • A. Set up Container Analysis to scan and report Common Vulnerabilities and Exposures.
  • B. Configure the containers in the build pipeline to always update themselves before release.
  • C. Reconfigure the existing operating system vulnerability software to exist inside the container.
  • D. Implement static code analysis tooling against the Docker files used to create the containers.
Show Suggested Answer
Suggested Answer: A 
Poprawna odpowiedź: A. Set up Container Analysis to scan and report Common Vulnerabilities and Exposures.

Wyjaśnienie:
W środowisku kontenerowym tradycyjne narzędzia do skanowania maszyn wirtualnych (VM) nie są skuteczne, ponieważ nie mają wglądu w warstwy obrazów kontenerów. Container Analysis (część usługi Artifact Analysis) to natywne rozwiązanie GCP, które automatycznie skanuje obrazy przechowywane w Artifact Registry lub Container Registry pod kątem znanych luk bezpieczeństwa (CVE). Jest to kluczowy element bezpiecznego łańcucha dostaw oprogramowania (Software Supply Chain Security).

Dlaczego inne odpowiedzi są błędne:
- B: Configure containers to always update themselves: Kontenery powinny być niezmienne (immutable). Wykonywanie "apt-get upgrade" wewnątrz kontenera podczas jego uruchamiania (runtime) jest poważnym błędem. Powoduje to, że środowiska są niepowtarzalne, wydłuża czas startu i utrudnia debugowanie. Aktualizacje powinny dziać się na etapie budowania obrazu.
- C: Operating system vulnerability software inside the container: Instalowanie ciężkich agentów skanujących wewnątrz każdego kontenera zaprzecza idei lekkości kontenerów ("bloatware") i znacznie zwiększa powierzchnię ataku. Skanowanie powinno odbywać się z zewnątrz obrazu (na poziomie rejestru).
- D: Static code analysis against Dockerfiles: Analiza Dockerfile (np. za pomocą narzędzi typu hadolint) jest dobrą praktyką (sprawdza czy nie używamy konta root, czy nie zostawiamy zbędnych warstw), ale nie wykryje podatności w bibliotekach zainstalowanych wewnątrz obrazu (np. podatna wersja OpenSSL czy log4j).

Hity i triki (GCP DevOps Exam):
- Container Analysis + Binary Authorization: To potężna para. Container Analysis skanuje, a Binary Authorization (BinAuthz) pozwala na wdrożenie do GKE TYLKO tych obrazów, które zostały pomyślnie przeskanowane i nie zawierają krytycznych luk.
- Shift-Left Security: Idea polegająca na skanowaniu jak najwcześniej w cyklu życia aplikacji (podczas budowania/przechowywania w rejestrze), a nie po wdrożeniu na produkcję.
- On-Demand Scanning API: Pozwala na skanowanie obrazów lokalnie przed ich wypchnięciem do rejestru, co przyspiesza pętlę informacji zwrotnej dla dewelopera.

Analiza i Podsumowanie (GCP DevOps Expert)

Zapewnienie bezpieczeństwa w nowoczesnych potokach CI/CD wymaga przejścia od skanowania infrastruktury (VM) do skanowania artefaktów (obrazów kontenerów). Google Cloud oferuje w pełni zarządzane narzędzia, które integrują się z rejestrami obrazów.

💡 Kluczowe wnioski:

  • Immutable Infrastructure: Nigdy nie aktualizuj kontenerów w trakcie ich działania. Zbuduj nowy obraz i zastąp stary.
  • CVE Scanning: Automatyczne skanowanie w Artifact Registry pozwala na ciągły monitoring podatności, nawet jeśli obraz został zbudowany dawno temu (ciągłe skanowanie).
  • Binary Authorization: Użyj tej usługi, aby narzucić politykę "no scan, no deploy".

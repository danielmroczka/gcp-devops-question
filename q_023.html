Question 23 / 201

Monitoring Stackdriver

You are developing a strategy for monitoring your Google Cloud Platform (GCP) projects in production using Stackdriver Workspaces. One of the requirements is to be able to quickly identify and react to production environment issues without false alerts from development and staging projects. You want to ensure that you adhere to the principle of least privilege when providing relevant team members with access to Stackdriver Workspaces. What should you do?

  • A. Grant relevant team members read access to all GCP production projects. Create Stackdriver workspaces inside each project.
  • B. Grant relevant team members the Project Viewer IAM role on all GCP production projects. Create Stackdriver workspaces inside each project.
  • C. Choose an existing GCP production project to host the monitoring workspace. Attach the production projects to this workspace. Grant relevant team members read access to the Stackdriver Workspace.
  • D. Create a new GCP monitoring project and create a Stackdriver Workspace inside it. Attach the production projects to this workspace. Grant relevant team members read access to the Stackdriver Workspace.
Show Suggested Answer
Suggested Answer: D 
Odpowiedź: D.

Wyjaśnienie:
Poprawną odpowiedzią jest **D (Create a new GCP monitoring project and create a Stackdriver Workspace inside it. Attach the production projects to this workspace. Grant relevant team members read access to the Stackdriver Workspace)**.

**Dlaczego D jest poprawne?**
Zalecaną przez Google praktyką dla środowisk produkcyjnych o dużej skali jest użycie **dedykowanego projektu monitorującego** (scoping project). Pozwala to na:
1.  **Centralizację:** Możesz podłączyć wiele projektów produkcyjnych (monitored projects) do jednego widoku (Metrics Scope / Workspace), co pozwala na szybką identyfikację problemów w całej infrastrukturze bez przełączania się między projektami.
2.  **Izolację:** Poprzez dołączenie tylko projektów produkcyjnych do tego konkretnego obszaru, eliminujesz "szum" i fałszywe alerty pochodzące ze środowisk deweloperskich czy stagingowych.
3.  **Zasadę najniższych uprawnień (Least Privilege):** Możesz nadać członkom zespołu uprawnienia `Monitoring Viewer` tylko w projekcie monitorującym. Dzięki temu widzą oni metryki i dashboardy dla wszystkich podłączonych projektów produkcyjnych, ale nie muszą posiadać żadnych uprawnień dostępu (np. Viewer czy Editor) w samych projektach produkcyjnych, co zwiększa bezpieczeństwo.

**Dlaczego pozostałe opcje są błędne?**
*   **A i B. Create Stackdriver workspaces inside each project:** Takie podejście wymusza na zespole operacyjnym sprawdzanie każdego projektu z osobna. Jest to nieefektywne ("toil") i znacznie wydłuża czas reakcji na incydenty (MTTR). Nadawanie ról w każdym projekcie z osobna jest również trudne do zarządzania i narusza zasadę centralnego zarządzania dostępem.
*   **C. Choose an existing GCP production project to host the monitoring workspace:** Choć technicznie możliwe, nie jest to zalecane. Jeśli projekt hostujący workspace zostanie usunięty lub napotka błędy konfiguracyjne podczas prac nad aplikacją, stracisz monitoring nad całą produkcją. Dedykowany projekt zapewnia czystą separację zasobów infrastrukturalnych (monitoring) od aplikacji.

### 💡 Hity i triki (Hints & Tricks)
- Pamiętaj: **Jeden Metrics Scope (Workspace) = Jeden widok na wiele projektów**.
- Szukaj słowa **"Dedicated"** lub **"New monitoring project"** w pytaniach o architekturę monitorowania wielu projektów.
- Rola `Monitoring Viewer` (lub `Stackdriver Accounts Viewer` w starszych wersjach) jest kluczowa dla zasady "least privilege" w monitoringu.

Analiza i Podsumowanie (AI)

Zarządzanie projektami w skali Enterprise wymaga podejścia hierarchicznego i scentralizowanego. To pytanie sprawdza znajomość architektury Cloud Monitoring i umiejętność stosowania dobrych praktyk bezpieczeństwa (IAM).

Kluczowe punkty:

  • Scoping Projects: Wykorzystanie jednego projektu jako "okna" na dane z innych projektów.
  • IAM Isolation: Rozdzielenie uprawnień do oglądania danych od uprawnień do zarządzania zasobami.
  • Environment Segregation: Unikanie mieszania alertów produkcyjnych z testowymi poprzez dedykowane obszary robocze.

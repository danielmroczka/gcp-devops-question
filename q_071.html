Question 71 / 201

GKE Kubernetes

You support a popular mobile game application deployed on Google Kubernetes Engine (GKE) across several Google Cloud regions. Each region has multiple Kubernetes clusters. You receive a report that none of the users in a specific region can connect to the application. You want to resolve the incident while following Site Reliability Engineering practices.

What should you do first?

  • A. Reroute the user traffic from the affected region to other regions that don't report issues.
  • B. Use Stackdriver Monitoring to check for a spike in CPU or memory usage for the affected region.
  • C. Add an extra node pool that consists of high memory and high CPU machine type instances to the cluster.
  • D. Use Stackdriver Logging to filter on the clusters in the affected region, and inspect error messages in the logs.
Show Suggested Answer
Suggested Answer: A 
Odpowiedź: A.

Wyjaśnienie:
Poprawna odpowiedź to A. Zgodnie z najlepszymi praktykami SRE (Site Reliability Engineering), w obliczu poważnej awarii (incident), pierwszym priorytetem jest **mitygacja** (ograniczenie skutków), a nie diagnoza.

Dlaczego odpowiedź A jest poprawna:
1. "Stop the bleeding": Rerouting ruchu to klasyczne działanie mające na celu natychmiastowe przywrócenie usługi użytkownikom. W systemach wieloregionalnych, globalny Load Balancer pozwala na szybkie odcięcie uszkodzonego regionu i przekierowanie użytkowników tam, gdzie system działa poprawnie.
2. Minimalizacja MTTR: Skierowanie ruchu do innych regionów drastycznie skraca czas przestoju (Downtime) z perspektywy klienta.
3. Spokój zespołu: Gdy usługa jest "tymczasowo naprawiona" dla użytkowników poprzez mitigację, zespół SRE może bez presji czasu przystąpić do analizy logów i monitoringu (Root Cause Analysis).

Analiza błędnych odpowiedzi:
- B i D: To kroki diagnostyczne. Chociaż są niezbędne, wykonanie ich jako **pierwszy** krok oznacza, że użytkownicy nadal doświadczają całkowitej awarii, podczas gdy Ty "czytasz logi". SRE uczy, że najpierw przywracamy działanie, potem szukamy przyczyny.
- C: Dodawanie zasobów (skalowanie pionowe lub poziome) bez wiedzy o przyczynie awarii jest działaniem "na oślep". Jeśli problemem jest błąd w kodzie lub awaria sieci regionalnej, dodatkowe węzły nie pomogą, a jedynie zwiększą koszty.

Hity i triki (Exam Tips):
- SRE Motto: **"Mitigate first, diagnose later"** (Najpierw mityguj, potem diagnozuj).
- Szukaj odpowiedzi, które przywracają usługę najszybciej: Rollback (wycofanie zmiany), Rerouting (zmiana trasy), Failover (przełączenie na zapas).
- Pamiętaj, że w chmurze GCP Global HTTP(S) Load Balancing potrafi automatycznie przekierowywać ruch (overflow), ale w przypadku awarii całego regionu może być wymagana manualna interwencja lub zmiana konfiguracji Cloud DNS / Traffic Management.

Analiza i Podsumowanie Dyskusji (AI)

Kluczowym konceptem w tym zadaniu jest hierarchia działań podczas incydentu. SRE nie szuka winnych ani przyczyn, dopóki pacjent (system) "krwawi". Przekierowanie ruchu to najskuteczniejsza metoda radzenia sobie z awariami regionalnymi (regional outages).

💡 Wskazówki i Triki (Exam Tips)

  • Na egzaminie zawsze odróżniaj działania **naprawcze** (np. rerouting) od **analitycznych** (np. sprawdzanie logów). Jeśli pytanie brzmi "What to do first?", naprawa zazwyczaj wygrywa.
  • Współczesne systemy Cloud DNS i Load Balancer mogą robić to automatycznie (health checks), ale inżynier musi wiedzieć, jak wymusić te działania.
  • Pamiętaj o "Error Budget" – jeśli incydent go wyczerpuje, Twoja polityka (z poprzednich pytań) powinna już być wdrożona.

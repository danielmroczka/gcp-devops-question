Question 48 / 201

Your team is designing a new application for deployment both inside and outside Google Cloud Platform (GCP). You need to collect detailed metrics such as system resource utilization. You want to use centralized GCP services while minimizing the amount of work required to set up this collection system.

What should you do?

  • A. Import the Stackdriver Profiler package, and configure it to relay function timing data to Stackdriver for further analysis.
  • B. Import the Stackdriver Debugger package, and configure the application to emit debug messages with timing information.
  • C. Instrument the code using a timing library, and publish the metrics via a health check endpoint that is scraped by Stackdriver.
  • D. Install an Application Performance Monitoring (APM) tool in both locations, and configure an export to a central data storage location for analysis.
Show Suggested Answer
Suggested Answer: A 
Odpowiedź: A.

Wyjaśnienie:
Poprawną odpowiedzią jest A, ponieważ Cloud Profiler jest usługą Google Cloud zaprojektowaną do zbierania szczegółowych danych o wydajności aplikacji przy minimalnym narzucie na system.

1. **A (Import the Stackdriver Profiler package):** Cloud Profiler to narzędzie typu "statistical profiler", które zbiera dane o użyciu procesora, pamięci i innych zasobów bezpośrednio z kodu aplikacji. Ważne jest to, że Profiler działa zarówno w Google Cloud, jak i poza nim (np. on-premise lub w innych chmurach), co spełnia wymóg "deployment both inside and outside GCP". Jest to rozwiązanie zarządzane (managed), co minimalizuje nakład pracy (Toil) potrzebny na konfigurację własnej infrastruktury do zbierania metryk.

Analiza niepoprawnych odpowiedzi:
- **B (Import the Stackdriver Debugger package):** Cloud Debugger służy do inspekcji stanu aplikacji (podgląd zmiennych, stos wywołań) bez zatrzymywania jej na produkcji. Nie jest narzędziem do zbierania metryk wydajnościowych ani monitorowania zużycia zasobów systemowych. (Uwaga: Usługa ta została wycofana i zastąpiona rozwiązaniami open-source).
- **C (Instrument the code using a timing library... scraped by Stackdriver):** To podejście wymaga znacznego nakładu pracy programistycznej (ręczna instrumentacja każdej istotnej funkcji) oraz konfiguracyjnej (ustawienie endpointu, zarządzanie scrapingiem). Narusza to warunek "minimizing the amount of work".
- **D (Install an APM tool in both locations and configure export):** Instalacja i konfiguracja zewnętrznego narzędzia APM (Application Performance Monitoring) w wielu lokalizacjach oraz zarządzanie centralnym składowiskiem danych jest znacznie bardziej pracochłonne niż użycie natywnego, zarządzanego agenta Cloud Profiler, który automatycznie przesyła dane do GCP.

Hity i triki (Hints & Tricks):
- Cloud Profiler ma bardzo niski narzut (zazwyczaj poniżej 1% CPU/RAM), co czyni go bezpiecznym do używania na produkcji.
- Jeśli widzisz "detailed metrics" i "function timing", myśl o **Profilowaniu**. Jeśli widzisz "centralized GCP services" i "outside GCP", szukaj usług z agentami/paczkami instalacyjnymi (Profiler, Logging, Monitoring).
- Profiler pomaga znaleźć "gorące ścieżki" w kodzie (najbardziej zasobożerne funkcje).

Przydatne linki:
- [Cloud Profiler overview](https://cloud.google.com/profiler/docs/about-profiler)
- [Profiling applications outside of Google Cloud](https://cloud.google.com/profiler/docs/profiling-outside-gcp)

Analiza i Podsumowanie Dyskusji (AI)

Zadanie to testuje znajomość zestawu narzędzi Google Cloud Observability. Kluczem jest rozróżnienie między monitorowaniem (metryki infrastrukturalne), logowaniem, a profilowaniem (głęboka analiza wydajności kodu).

💡 Wskazówki i Triki (Exam Tips)

  • Cloud Profiler = Analiza wydajności na poziomie kodu (CPU, Heap, Wall Time).
  • Minimalny narzut (Overhead) to główna zaleta statystycznego profilowania w GCP.
  • Gdy firma chce "minimalizować pracę", zawsze szukaj natywnych rozwiązań typu "import package" lub "install agent" zamiast budowania własnych systemów agregacji.

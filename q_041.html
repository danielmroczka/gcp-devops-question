Question 41 / 201

You support a high-traffic web application that runs on Google Cloud Platform (GCP). You need to measure application reliability from a user perspective without making any engineering changes to it. What should you do? (Choose two.)

  • A. Review current application metrics and add new ones as needed.
  • B. Modify the code to capture additional information for user interaction.
  • C. Analyze the web proxy logs only and capture response time of each request.
  • D. Create new synthetic clients to simulate a user journey using the application.
  • E. Use current and historic Request Logs to trace customer interaction with the application.
Show Suggested Answer
Suggested Answer: DE 
Odpowiedź: DE.

Wyjaśnienie:
Poprawnymi odpowiedziami są D i E, ponieważ obie metody pozwalają na mierzenie niezawodności z perspektywy użytkownika bez ingerencji w kod źródłowy aplikacji (tzw. Black-box monitoring).

1. **D (Create new synthetic clients to simulate a user journey):** Monitorowanie syntetyczne (np. Cloud Monitoring Uptime Checks) polega na emulowaniu zachowań użytkowników przez zewnętrzne skrypty lub sondy. Pozwala to na proaktywne wykrywanie problemów z dostępnością i wydajnością z różnych lokalizacji geograficznych, nie wymagając żadnych zmian w samej aplikacji.
2. **E (Use current and historic Request Logs to trace customer interaction):** Analiza logów żądań (Request Logs), generowanych przez infrastrukturę (np. Cloud Load Balancing), pozwala na badanie rzeczywistego ruchu użytkowników. Logi te zawierają kody odpowiedzi HTTP, czasy latencji i ścieżki dostępu, co umożliwia precyzyjne wyliczenie wskaźników SLI (Service Level Indicators) bez modyfikacji kodu.

Analiza niepoprawnych odpowiedzi:
- **A: Review current application metrics and add new ones as needed.** Dodawanie nowych metryk aplikacji zazwyczaj wymaga instrumentacji kodu (np. użycie bibliotek OpenTelemetry lub Prometheus), co narusza warunek braku zmian inżynieryjnych.
- **B: Modify the code to capture additional information for user interaction.** Ta opcja bezpośrednio narusza główne ograniczenie zadania ("without making any engineering changes").
- **C: Analyze the web proxy logs only and capture response time of each request.** Choć analiza logów jest słuszna, ograniczenie się *tylko* do logów proxy i *tylko* do czasu odpowiedzi jest mniej kompleksowe niż połączenie testów syntetycznych (które sprawdzają dostępność nawet gdy nie ma ruchu) i logów żądań (które dają pełny obraz interakcji).

Hity i triki (Hints & Tricks):
- W SRE wyróżniamy **Black-box monitoring** (testowanie z zewnątrz, np. syntetyki) oraz **White-box monitoring** (metryki z wewnątrz aplikacji, np. eksportowane przez kod). Jeśli zadanie zabrania zmian w kodzie, szukaj rozwiązań Black-box.
- SLI (Service Level Indicator) dla niezawodności to często stosunek zapytań zakończonych sukcesem do wszystkich zapytań. Logi Load Balancera są idealnym źródłem tych danych w GCP.

Analiza i Podsumowanie Dyskusji (AI)

Kluczem do rozwiązania tego pytania jest zrozumienie ograniczenia "no engineering changes". Wymusza to zastosowanie metod monitorowania zewnętrznego (Black-box) lub wykorzystanie istniejących logów infrastrukturalnych.

💡 Wskazówki i Triki (Exam Tips)

  • Gdy widzisz "without making changes to code", myśl o: Uptime Checks, Cloud Logging, Cloud Load Balancing logs.
  • Mierzenie z "user perspective" sugeruje, że musimy widzieć to, co widzi klient (zewnętrzne IP, kody 2xx/5xx, latencja na brzegu sieci).
  • Zawsze odróżniaj metryki aplikacyjne (White-box) od infrastrukturalnych/zewnętrznych (Black-box).

Question 108 / 201

Cloud Build

You are creating a CI/CD pipeline in Cloud Build to build an application container image. The application code is stored in GitHub. Your company requires that production image builds are only run against the main branch and that the change control team approves all pushes to the main branch. You want the image build to be as automated as possible.

What should you do? (Choose two.)

  • A. Create a trigger on the Cloud Build job. Set the repository event setting to 'Pull request'.
  • B. Add the OWNERS file to the Included files filter on the trigger.
  • C. Create a trigger on the Cloud Build job. Set the repository event setting to 'Push to a branch'
  • D. Configure a branch protection rule for the main branch on the repository.
  • E. Enable the Approval option on the trigger.
Show Suggested Answer
Suggested Answer: CD 
Odpowiedź: CD

Wyjaśnienie:
- Opcja C (Trigger "Push to a branch"): Jest to podstawowy sposób na uruchomienie Cloud Build automatycznie, gdy kod trafi do gałęzi `main`.
- Opcja D (Branch protection): Jest to wymagane przez firmę w celu zapewnienia, że wszystkie zmiany w `main` są zatwierdzone przez "change control team" (np. poprzez wymagane code review lub status checks przed merge'em). Cloud Build uruchomi się dopiero, gdy kod pomyślnie trafi do `main` po przejściu procedur ochronnych.

Wyjaśnienie niepoprawnych odpowiedzi:
- Opcja A: "Pull request" trigger uruchomiłby budowanie przy każdym PR, a nie dopiero po "pushes to the main branch" (czyli po merge'u).
- Opcja B: Plik `OWNERS` służy do zarządzania uprawnieniami wewnątrz repozytorium (kto może zatwierdzać zmiany), a nie do sterowania triggerem Cloud Build.
- Opcja E: Cloud Build nie posiada wbudowanej opcji "Approval" na samym poziomie konfiguracji triggera, która realizowałaby proces "change control" w ten sposób.

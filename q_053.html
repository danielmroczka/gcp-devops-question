Question 53 / 201

Terraform

Your team of Infrastructure DevOps Engineers is growing, and you are starting to use Terraform to manage infrastructure. You need a way to implement code versioning and to share code with other team members.

What should you do?

  • A. Store the Terraform code in a version-control system. Establish procedures for pushing new versions and merging with the master.
  • B. Store the Terraform code in a network shared folder with child folders for each version release. Ensure that everyone works on different files.
  • C. Store the Terraform code in a Cloud Storage bucket using object versioning. Give access to the bucket to every team member so they can download the files.
  • D. Store the Terraform code in a shared Google Drive folder so it syncs automatically to every team member's computer. Organize files with a naming convention that identifies each new version.
Show Suggested Answer
Suggested Answer: A 
Odpowiedź: A.

Wyjaśnienie:
Poprawną odpowiedzią jest A, ponieważ stosowanie Systemu Kontroli Wersji (VCS), takiego jak Git, jest fundamentem praktyk Infrastructure as Code (IaC) oraz DevOps.

1. **A (Store the Terraform code in a version-control system):** 
   - **Wersjonowanie:** VCS pozwala na śledzenie każdej zmiany w kodzie infrastruktury, identyfikację autorów zmian oraz łatwe wycofywanie (rollback) do poprzednich, stabilnych wersji.
   - **Współpraca:** Mechanizmy takie jak gałęzie (branches) pozwalają wielu inżynierom pracować nad różnymi elementami infrastruktury jednocześnie bez ryzyka nadpisania swojej pracy.
   - **Proces zatwierdzania:** Procedury "pushing and merging" zazwyczaj obejmują Code Review (Pull/Merge Requests), co pozwala na weryfikację kodu pod kątem bezpieczeństwa i poprawności przed wdrożeniem zmian.

Analiza niepoprawnych odpowiedzi:
- **B (Network shared folder):** Foldery sieciowe nie oferują historii zmian, zarządzania konfliktami (gdy dwie osoby edytują ten sam plik) ani mechanizmów przeglądu kodu. Jest to rozwiązanie bardzo podatne na błędy ludzkie.
- **C (Cloud Storage bucket using object versioning):** Choć Cloud Storage oferuje wersjonowanie obiektów, nie jest to system kontroli wersji kodu. Pobieranie plików, edytowanie ich lokalnie i ręczne przesyłanie z powrotem jest procesem mozolnym (Toil) i nie pozwala na efektywną pracę zespołową (brak mechanizmu `merge`).
- **D (Shared Google Drive folder):** Podobnie jak folder sieciowy, Google Drive nie jest przeznaczony do przechowywania kodu źródłowego. Synchronizacja plików może prowadzić do nieprzewidywalnych konfliktów w plikach `.tf`, a brak zintegrowanego systemu gałęzi i przeglądu kodu dyskwalifikuje to rozwiązanie w profesjonalnym środowisku.

Hity i triki (Hints & Tricks):
- Wszystko, co jest tekstem (kod aplikacji, konfiguracja YAML, skrypty Terraform), powinno trafiać do **Gita**.
- W Terraformie, oprócz samego kodu, kluczowe jest zarządzanie plikiem stanu (**State File**). O ile kod trzymamy w Gicie, o tyle plik stanu powinien być przechowywany w tzw. "Remote Backend" (np. GCS Bucket z włączonym blokowaniem/locking).
- Korzystanie z Gita umożliwia wdrożenie **GitOps**, gdzie zmiany w infrastrukturze są automatycznie aplikowane po zaakceptowaniu Pull Requesta.

Analiza i Podsumowanie Dyskusji (AI)

To pytanie sprawdza znajomość podstawowych zasad inżynierii oprogramowania stosowanych w infrastrukturze. IaC (Infrastructure as Code) wymaga traktowania definicji serwerów i sieci tak samo jak kodu aplikacji.

💡 Wskazówki i Triki (Exam Tips)

  • VCS = Git. Zawsze szukaj odpowiedzi z Git/VCS w kontekście zarządzania kodem lub konfiguracją.
  • Współpraca w zespole DevOps bez Gita jest praktycznie niemożliwa do skalowania.
  • Pamiętaj: "Code is king, Git is the castle".

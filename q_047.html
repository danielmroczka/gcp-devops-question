Question 47 / 201

Monitoring Stackdriver

You are managing an application that exposes an HTTP endpoint without using a load balancer. The latency of the HTTP responses is important for the user experience. You want to understand what HTTP latencies all of your users are experiencing. You use Stackdriver Monitoring. What should you do?

  • A. In your application, create a metric with a metricKind set to DELTA and a valueType set to DOUBLE. In Stackdriver's Metrics Explorer, use a Stacked Bar graph to visualize the metric.
  • B. In your application, create a metric with a metricKind set to CUMULATIVE and a valueType set to DOUBLE. In Stackdriver's Metrics Explorer, use a Line graph to visualize the metric.
  • C. In your application, create a metric with a metricKind set to GAUGE and a valueType set to DISTRIBUTION. In Stackdriver's Metrics Explorer, use a Heatmap graph to visualize the metric.
  • D. In your application, create a metric with a metricKind set to METRIC_KIND_UNSPECIFIED and a valueType set to INT64. In Stackdriver's Metrics Explorer, use a Stacked Area graph to visualize the metric.
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Poprawną odpowiedzią jest C, ponieważ wizualizacja rozkładu latencji (histograms) dla wielu użytkowników najlepiej realizowana jest przy użyciu typu wartości `DISTRIBUTION` oraz wykresu typu `Heatmap`.

1. **C (GAUGE and DISTRIBUTION with Heatmap):** 
   - **GAUGE:** Metryka typu Gauge reprezentuje wartość w konkretnym punkcie czasowym (np. latencja ostatniego żądania).
   - **DISTRIBUTION:** Ten typ wartości pozwala na zbieranie populacji danych i dzielenie ich na "kubełki" (buckets). Jest to niezbędne, aby zrozumieć nie tylko średnią latencję, ale także percentyle (np. p95, p99), które najlepiej oddają doświadczenie użytkowników.
   - **Heatmap:** Mapa cieplna (Heatmap) w Cloud Monitoring wizualizuje dane typu `DISTRIBUTION` w czasie. Kolory reprezentują zagęszczenie próbek w danym zakresie latencji, co pozwala natychmiast zauważyć anomalie lub "rozjeżdżanie się" czasów odpowiedzi.

Analiza niepoprawnych odpowiedzi:
- **A (DELTA and DOUBLE with Stacked Bar):** Typ `DELTA` mierzy zmianę wartości w czasie, a `DOUBLE` to pojedyncza liczba zmiennoprzecinkowa. Wykres słupkowy (Stacked Bar) nie nadaje się do ciągłego monitorowania rozkładu latencji tysięcy żądań w czasie.
- **B (CUMULATIVE and DOUBLE with Line graph):** Typ `CUMULATIVE` służy do liczników, które tylko rosną (np. całkowita liczba bajtów). Wykres liniowy pokazałby tylko jedną wartość (np. średnią), co ukrywa istotne informacje o "ogonie" latencji (użytkownikach doświadczających bardzo wolnych odpowiedzi).
- **D (METRIC_KIND_UNSPECIFIED and INT64 with Stacked Area):** Nieokreślony typ metryki i pojedyncza liczba całkowita (`INT64`) nie pozwalają na modelowanie statystycznego rozkładu latencji.

Hity i triki (Hints & Tricks):
- Słowo klucz "latencies experienced by all users" sugeruje potrzebę zobaczenia pełnego spektrum danych, a nie tylko średniej. Zawsze wtedy szukaj **DISTRIBUTION**.
- Heatmapy są idealne do wykrywania "modalności" rozkładu (np. gdy część użytkowników obsługiwana jest z cache, a część z bazy danych – zobaczysz dwa wyraźne pasma na mapie).
- Pamiętaj o różnicy: **Gauge** (obecny stan), **Delta** (zmiana od ostatniego odczytu), **Cumulative** (suma od początku).

💡 Wskazówki i Triki (Exam Tips)

  • Latencja = Distribution. Średnia kłamie (Average lies), percentyle mówią prawdę.
  • Heatmapa to jedyny sensowny sposób na wizualizację typu Distribution w GCP.
  • Zapamiętaj: Jeśli chcesz mierzyć "experience of all users", musisz widzieć rozkład, a nie pojedynczy punkt.

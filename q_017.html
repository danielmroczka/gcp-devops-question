Question 17 / 201

GKE Kubernetes

You support an e-commerce application that runs on a large Google Kubernetes Engine (GKE) cluster deployed on-premises and on Google Cloud Platform. The application consists of microservices that run in containers. You want to identify containers that are using the most CPU and memory.

What should you do?

  • A. Use Stackdriver Kubernetes Engine Monitoring.
  • B. Use Prometheus to collect and aggregate logs per container, and then analyze the results in Grafana.
  • C. Use the Stackdriver Monitoring API to create custom metrics, and then organize your containers using groups.
  • D. Use Stackdriver Logging to export application logs to BigQuery, aggregate logs per container, and then analyze CPU and memory consumption.
Show Suggested Answer
Suggested Answer: A 
Odpowiedź: A.

Wyjaśnienie:
Poprawną odpowiedzią jest **A (Use Stackdriver Kubernetes Engine Monitoring)**.

**Dlaczego A jest poprawne?**
Stackdriver Kubernetes Engine Monitoring (obecnie znany jako **Google Cloud Observability** lub **Cloud Monitoring for GKE**) jest natywnym rozwiązaniem Google Cloud do monitorowania wydajności klastrów GKE. Został on zaprojektowany tak, aby automatycznie zbierać metryki systemowe (takie jak zużycie procesora i pamięci RAM) bezpośrednio z kontenerów i podów. Co ważne w kontekście pytania, obsługuje on również klastry Anthos (GKE on-prem), co pozwala na uzyskanie spójnego widoku w środowisku hybrydowym. Umożliwia łatwe sortowanie i identyfikację zasobochłonnych kontenerów za pomocą dedykowanych dashboardów.

**Dlaczego pozostałe opcje są błędne?**
*   **B. Use Prometheus to collect and aggregate logs per container, and then analyze the results in Grafana:** Prometheus służy do zbierania *metryk*, a nie *logów*. Chociaż Prometheus jest standardem w ekosystemie Kubernetes, wymaga on samodzielnego zarządzania (instalacja, aktualizacje, skalowanie), co zwiększa narzut operacyjny (toil) w porównaniu do natywnego rozwiązania Google.
*   **C. Use the Stackdriver Monitoring API to create custom metrics, and then organize your containers using groups:** Tworzenie własnych metryk (custom metrics) do monitorowania zużycia procesora i pamięci jest niepotrzebne, ponieważ te metryki są już standardowo dostępne (out-of-the-box). Ręczne tworzenie grup byłoby bardzo pracochłonne i trudne w utrzymaniu przy dużej skali klastra.
*   **D. Use Stackdriver Logging to export application logs to BigQuery, aggregate logs per container, and then analyze CPU and memory consumption:** Logi (zdarzenia tekstowe) nie są odpowiednim źródłem danych do analizy zużycia zasobów w czasie rzeczywistym. Eksportowanie ogromnej ilości logów do BigQuery tylko po to, by wyciągnąć z nich informacje o CPU, byłoby niezwykle kosztowne, powolne i mało precyzyjne.

### 💡 Hity i triki (Hints & Tricks)
- Pamiętaj: **Metryki (CPU/RAM) != Logi (Zdarzenia)**. Do monitorowania zasobów zawsze używaj narzędzi do metryk (Monitoring), a nie do logów (Logging).
- Jeśli widzisz nazwę "Stackdriver", wiedz, że odnosi się ona do obecnego **Google Cloud Operations Suite**. Na egzaminie starsze nazewnictwo wciąż może się pojawiać.
- Natywne rozwiązania (Managed Services) są w świecie GCP zazwyczaj preferowane nad rozwiązaniami typu "zrób to sam" (jak samodzielny Prometheus), chyba że wymogiem jest uniknięcie "vendor lock-in".

Analiza i Podsumowanie (AI)

To pytanie sprawdza Twoją umiejętność wyboru właściwego narzędzia do monitorowania wydajności w środowisku hybrydowym. Kluczowym elementem jest zrozumienie różnicy między metrykami a logami oraz korzyści płynących z usług zarządzanych przez GCP.

Kluczowe punkty:

  • Unified Observability: Możliwość monitorowania GKE w chmurze i on-prem (Anthos) w jednym miejscu.
  • Resource Efficiency: Identyfikacja "top talkers" (kontenerów zużywających najwięcej zasobów) jest podstawową funkcją Cloud Monitoring.
  • Toil Reduction: Wybór rozwiązania, które wymaga najmniej konfiguracji i utrzymania.

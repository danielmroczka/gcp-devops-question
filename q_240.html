GCP DevOps

Your team at LumenStream operates a latency sensitive API on Google Kubernetes Engine and you must keep performance steady. The workload reacts poorly to changes in available CPU and memory when the cluster runs automatic node pool upgrades. What should you implement to preserve the expected performance during these upgrade cycles?

  • A. Enable “Vertical Pod Autoscaling” to automatically adjust CPU and memory requests for the pods based on observed usage
  • B. Turn on “surge upgrades” for the GKE node pool so new nodes come online before existing nodes are drained
  • C. Use “node affinity” rules so the pods schedule onto nodes with specific labels that indicate dedicated capacity
  • D. Define a “PodDisruptionBudget” that limits the number of pods that can be evicted during maintenance
Show Suggested Answer
Suggested Answer: D 
Odpowiedź: D

Wyjaśnienie:
Poprawna odpowiedź to D (PodDisruptionBudget). PodDisruptionBudget (PDB) jest jedynym mechanizmem z listy, który aktywnie zarządza dostępnością aplikacji podczas planowanych zakłóceń (voluntary disruptions), takich jak automatyczne aktualizacje węzłów w GKE. 
PDB gwarantuje, że podczas eksmisji podów (np. przez `kubectl drain` podczas aktualizacji), zawsze pozostanie w ruchu zdefiniowana przez Ciebie minimalna liczba (lub procent) replik (minAvailable) lub dopuszczalna liczba niedostępnych replik (maxUnavailable). 
Dzięki temu wydajność aplikacji pozostaje przewidywalna, nawet gdy węzły pod nią są wymieniane na nowe wersje.

Wyjaśnienie błędnych odpowiedzi:
- A: VPA (Vertical Pod Autoscaling) dostosowuje `requests` i `limits` podów, ale nie ma wpływu na proces eksmisji podów podczas aktualizacji węzłów. Może wręcz pogorszyć sytuację, powodując niepotrzebne restarty podów w krytycznym momencie.
- B: Surge upgrades (dodatkowe węzły) poprawiają ogólną przepustowość aktualizacji węzłów, ale nie kontrolują, ile podów zniknie z istniejących węzłów w danym momencie. To proces infrastrukturalny, nie aplikacyjny.
- C: Node Affinity (powinowactwo do węzłów) definiuje zasady rozmieszczenia podów. Nawet jeśli użyjesz bardzo restrykcyjnego Affinity, podczas aktualizacji węzła, na którym działają pody, muszą one zostać usunięte (drained) i przeniesione, co bez PDB może naruszyć dostępność.

Analiza i Podsumowanie Dyskusji (AI)

To pytanie testuje Twoją znajomość narzędzi do utrzymania wysokiej dostępności (HA) w Kubernetes podczas operacji typu "planowane zakłócenia" (Voluntary Disruptions).

Dlaczego D jest poprawne?

PodDisruptionBudget (PDB) to kontrakt między właścicielem aplikacji a klastrem. Gwarantuje on, że podczas zdarzeń takich jak aktualizacja węzłów GKE (które automatycznie drenują węzły), klaster nie usunie więcej podów, niż pozwala na to budżet. To jedyny sposób, aby wymusić na procesie aktualizacji "powolne" przenoszenie aplikacji, zapobiegając utracie wydajności wynikającej z nagłego spadku liczby dostępnych instancji.

Dlaczego pozostałe są błędne?

  • A (VPA): To narzędzie do optymalizacji zasobów (`CPU`/`Memory`). Podczas upgrade'u węzłów nie chroni podów przed eksmisją, a wręcz zwiększa ryzyko niestabilności w fazie przejściowej.
  • B (Surge Upgrades): Mechanizm GKE przyspieszający proces upgrade'u węzłów. Choć pomaga zwiększyć całkowitą liczbę dostępnych zasobów w klastrze, nie narzuca żadnych ograniczeń aplikacji odnośnie minimalnej liczby podów, które muszą działać.
  • C (Node Affinity): To deklaratywna konfiguracja, gdzie pod "chce" być uruchomiony. Nie posiada mechanizmów zarządzania przerwami w działaniu aplikacji (disruption management).

💡 Wskazówki i Triki (Exam Tips)

  • Kluczowe słowo "Performance steady/latency sensitive": Zawsze kojarz z koniecznością kontroli eksmisji podów podczas prac serwisowych -> PodDisruptionBudget.
  • Rodzaj zakłóceń: PDB chroni tylko przed dobrowolnymi zakłóceniami (planowane prace). Nie zabezpiecza przed awarią sprzętową węzła (involuntary disruption).
  • PDB + HPA: Często w profesjonalnych projektach PDB jest używane razem z HPA, aby utrzymać wydajność przy dynamicznie zmieniającej się skali aplikacji.

GCP DevOps

Your team at LumenStream operates a latency sensitive API on Google Kubernetes Engine and you must keep performance steady. The workload reacts poorly to changes in available CPU and memory when the cluster runs automatic node pool upgrades. What should you implement to preserve the expected performance during these upgrade cycles?

  • A. Enable “Vertical Pod Autoscaling” to automatically adjust CPU and memory requests for the pods based on observed usage
  • B. Turn on “surge upgrades” for the GKE node pool so new nodes come online before existing nodes are drained
  • C. Use “node affinity” rules so the pods schedule onto nodes with specific labels that indicate dedicated capacity
  • D. Define a “PodDisruptionBudget” that limits the number of pods that can be evicted during maintenance
Show Suggested Answer
Suggested Answer: D 
Odpowiedź: D

Wyjaśnienie:
Poprawna odpowiedź to D (PodDisruptionBudget). PodDisruptionBudget (PDB) pozwala na określenie minimalnej liczby lub procentu podów, które muszą być dostępne w trakcie planowanych zakłóceń (np. aktualizacja węzłów GKE), zapobiegając nadmiernemu usuwaniu instancji.

Wyjaśnienie błędnych odpowiedzi:
- A: VPA automatycznie dostosowuje zasoby, ale w trakcie aktualizacji może powodować niepożądane restarty, co nie rozwiązuje problemu dostępności.
- B: Surge upgrades (dodatkowe węzły) zwiększają ogólną przepustowość aktualizacji, ale bez PDB Kubernetes nadal może eksmitować zbyt wiele podów na istniejących węzłach.
- C: Node Affinity określa, gdzie pod może zostać uruchomiony, co nie chroni przed eksmisją podczas konserwacji.

Analiza i Podsumowanie Dyskusji (AI)

Pytanie sprawdza zrozumienie mechanizmów ochrony dostępności usług (High Availability) w środowisku Kubernetes podczas operacji serwisowych.

Dlaczego D jest poprawne?

PodDisruptionBudget (PDB) jest kluczowym zasobem Kubernetes służącym do definiowania reguł ograniczających liczbę jednoczesnych awarii podów podczas działań konserwacyjnych (jak `kubectl drain` podczas aktualizacji węzłów GKE). Dzięki PDB gwarantujemy, że nasza aplikacja zachowa zdefiniowaną minimalną liczbę replik dostępnych dla ruchu użytkowników.

Dlaczego pozostałe są błędne?

  • A (VPA): VPA służy do optymalizacji zasobów, a nie do ochrony dostępności. Restartowanie podów w trakcie aktualizacji węzłów tylko zwiększa ryzyko przestojów.
  • B (Surge Upgrades): To technika przyspieszająca aktualizację węzłów poprzez tworzenie nowych przed usunięciem starych. Nie gwarantuje jednak, że z istniejących węzłów nie zostanie usuniętych zbyt wiele podów aplikacji naraz.
  • C (Node Affinity): Określa umiejscowienie pody. Podczas opróżniania węzła (draining) pody i tak muszą zostać przeniesione, niezależnie od reguł powinowactwa.

💡 Wskazówki i Triki (Exam Tips)

  • Jeśli w pytaniu pojawia się problem "utraty wydajności/dostępności podczas konserwacji węzłów", pierwszym słowem, którego powinieneś szukać w odpowiedziach, jest PodDisruptionBudget.
  • Pamiętaj: PDB chroni przed *dobrowolnymi* zakłóceniami (voluntary disruptions), czyli takimi, które inicjuje administrator lub system (np. aktualizacja GKE), a nie przed awariami sprzętowymi.

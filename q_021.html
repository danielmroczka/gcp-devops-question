Question 21 / 201

Cloud Build

Your application images are built using Cloud Build and pushed to Google Container Registry (GCR). You want to be able to specify a particular version of your application for deployment based on the release version tagged in source control.

What should you do when you push the image?

  • A. Reference the image digest in the source control tag.
  • B. Supply the source control tag as a parameter within the image name.
  • C. Use Cloud Build to include the release version tag in the application image.
  • D. Use GCR digest versioning to match the image to the tag in source control.
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Poprawną odpowiedzią jest **C (Use Cloud Build to include the release version tag in the application image)**.

**Dlaczego C jest poprawne?**
W procesach CI/CD kluczowe jest zachowanie spójności między kodem źródłowym a artefaktem (obrazem kontenera). Cloud Build umożliwia automatyczne pobranie nazwy tagu z systemu kontroli wersji (np. GitHub, Bitbucket, Cloud Source Repositories) i użycie jej do otagowania budowanego obrazu w Google Container Registry (GCR) lub Artifact Registry. Robi się to za pomocą tzw. **substytucji (substitutions)**, takich jak `${TAG_NAME}`. Dzięki temu, jeśli w Git otagujesz kod jako `v1.2.0`, Cloud Build zbuduje obraz i wypchnie go do rejestru pod nazwą `gcr.io/[PROJECT_ID]/my-app:v1.2.0`. Pozwala to na łatwe wskazanie konkretnej wersji podczas wdrożenia.

**Dlaczego pozostałe opcje są błędne?**
*   **A. Reference the image digest in the source control tag:** Digest obrazu (skrót SHA256) jest generowany przez rejestr kontenerów dopiero *po* wypchnięciu obrazu. Próba umieszczenia go w tagu kontroli źródła (który zazwyczaj inicjuje proces budowania) jest logicznie błędna ("co było pierwsze: jajko czy kura"). Choć digest jest najbezpieczniejszą metodą identyfikacji obrazu, nie służy on do mapowania tagów Git na nazwy obrazów w ten sposób.
*   **B. Supply the source control tag as a parameter within the image name:** Phrasing "parameter within the image name" jest mało precyzyjny technicznie. W ekosystemie Docker wersjonowanie odbywa się poprzez **tagi** (część po dwukropku w nazwie obrazu), a nie parametry wewnątrz nazwy. Opcja C precyzyjniej opisuje ten proces.
*   **D. Use GCR digest versioning to match the image to the tag in source control:** GCR automatycznie wersjonuje obrazy za pomocą digestów, ale są one nieczytelne dla człowieka (np. `sha256:45b...`). Samo użycie digestów nie zapewnia automatycznego powiązania z konkretnym tagiem w systemie kontroli wersji bez dodatkowego kroku tagowania opisanego w punkcie C.

### 💡 Hity i triki (Hints & Tricks)
- Pamiętaj o zmiennych w Cloud Build: `${TAG_NAME}` (dla tagów), `${COMMIT_SHA}` (dla konkretnego commitu), `${BRANCH_NAME}` (dla gałęzi).
- Dobrą praktyką (Best Practice) jest tagowanie obrazu tagiem Git oraz unikalnym identyfikatorem buildu, aby zapewnić pełną identyfikowalność (Traceability).
- Nigdy nie polegaj na tagu `:latest` na produkcji! Zawsze używaj konkretnych wersji (tagów) lub digestów.

Analiza i Podsumowanie (AI)

Zarządzanie wersjami (Release Management) to jeden z głównych filarów egzaminu DevOps. Musisz wiedzieć, jak połączyć artefakty z ich kodem źródłowym.

Kluczowe zagadnienia:

  • Traceability: Możliwość sprawdzenia, jaki kod znajduje się w konkretnym obrazie.
  • Automation: Automatyczne tagowanie obrazów przez system CI/CD (Cloud Build).
  • Docker Tagging: Zrozumienie różnicy między tagiem (mutable) a digestem (immutable).

Question 39 / 201

Cloud Build

You have a CI/CD pipeline that uses Cloud Build to build new Docker images and push them to Docker Hub. You use Git for code versioning. After making a change in the Cloud Build YAML configuration, you notice that no new artifacts are being built by the pipeline. You need to resolve the issue following Site Reliability Engineering practices.

What should you do?

  • A. Disable the CI pipeline and revert to manually building and pushing the artifacts.
  • B. Change the CI pipeline to push the artifacts to Container Registry instead of Docker Hub.
  • C. Upload the configuration YAML file to Cloud Storage and use Error Reporting to identify and fix the issue.
  • D. Run a Git compare between the previous and current Cloud Build Configuration files to find and fix the bug.
Show Suggested Answer
Suggested Answer: D 
Odpowiedź: D.

Wyjaśnienie:
Poprawna odpowiedź to D. Zgodnie z praktykami SRE i DevOps, konfiguracja potoków CI/CD (np. pliki YAML w Cloud Build) powinna być traktowana jako kod (Configuration as Code). Gdy automatyzacja przestaje działać tuż po wprowadzeniu zmian, najszybszą i najbardziej skuteczną metodą diagnostyki jest sprawdzenie, co dokładnie zostało zmienione. Polecenie `git diff` (lub porównanie wersji w interfejsie webowym systemu Git) pozwala natychmiast wyłapać błędy składniowe, literówki w nazwach obrazów czy błędne wcięcia (indendację), które są częstą przyczyną awarii plików YAML.

Dlaczego inne odpowiedzi są błędne:
A. Powrót do budowania manualnego to drastyczne zwiększenie "Toil" (mozolnej, powtarzalnej pracy). SRE dąży do naprawy automatyzacji, a nie jej porzucenia przy pierwszej trudności. Manualne wdrożenia są również bardziej podatne na błędy ludzkie.
B. Zmiana Docker Hub na Container Registry to zmiana infrastrukturalna, która nie adresuje przyczyny błędu w samej konfiguracji. To działanie "na oślep", które nie wynika z analizy problemu.
C. Cloud Error Reporting służy do monitorowania błędów (wyjątków) generowanych przez uruchomiony kod aplikacji w czasie rzeczywistym. Nie jest to narzędzie przeznaczone do sprawdzania poprawności plików konfiguracyjnych YAML.

Hity i triki (Exam Tips):
- **Troubleshooting Gold Rule:** Jeśli coś działało i przestało po zmianie -> sprawdź "diff".
- **YAML to kod:** Traktuj pliki konfiguracji pipeline'ów z taką samą powagą jak kod źródłowy aplikacji. Pamiętaj o testowaniu zmian w konfiguracji na oddzielnych branchach.
- **SRE Mindset:** Zamiast omijać błędy (manual build), naprawiaj przyczynę źródłową w automatyzacji.

Analiza i Podsumowanie Dyskusji (AI)

Kwestia ta dotyczy "Mean Time to Detect" (MTTD) i "Mean Time to Repair" (MTTR). W środowisku GitOps najkrótsza droga do naprawy prowadzi przez historię commitów.

💡 Wskazówki i Triki (Exam Tips)

  • Cloud Build local builder: Wspomnijmy o narzędziu `cloud-build-local`, które pozwala na testowanie plików YAML na własnej maszynie przed ich wypchnięciem do repozytorium – to zapobiega takim sytuacjom.
  • Indentation matters: W YAML-u spacje są kluczowe. Często to właśnie brak jednej spacji psuje cały pipeline, a `git diff` to najszybszy sposób, by to zobaczyć.
  • Blame-free culture: Nawet jeśli diff pokaże, kto popełnił błąd, SRE skupia się na tym, jak poprawić proces (np. dodać linter do pre-commit hooka), a nie na wytykaniu palcami.

Question 44 / 201

GKE Kubernetes SLI

Your team has recently deployed an NGINX-based application into Google Kubernetes Engine (GKE) and has exposed it to the public via an HTTP Google Cloud Load Balancer (GCLB) ingress. You want to scale the deployment of the application's frontend using an appropriate Service Level Indicator (SLI).

What should you do?

  • A. Configure the horizontal pod autoscaler to use the average response time from the Liveness and Readiness probes.
  • B. Configure the vertical pod autoscaler in GKE and enable the cluster autoscaler to scale the cluster as pods expand.
  • C. Install the Stackdriver custom metrics adapter and configure a horizontal pod autoscaler to use the number of requests provided by the GCLB.
  • D. Expose the NGINX stats endpoint and configure the horizontal pod autoscaler to use the request metrics exposed by the NGINX deployment.
Show Suggested Answer
Suggested Answer: C 
Odpowiedź: C.

Wyjaśnienie:
Poprawną odpowiedzią jest C, ponieważ skalowanie w oparciu o liczbę żądań z Load Balancera (GCLB) wymaga dostarczenia tych zewnętrznych metryk do Horizontal Pod Autoscalera (HPA) w klastrze GKE.

1. **C (Install the Stackdriver custom metrics adapter and configure a horizontal pod autoscaler to use the number of requests provided by the GCLB):** HPA natywnie potrafi skalować w oparciu o użycie CPU i pamięci. Aby skalować na podstawie innych metryk (np. ruch HTTP na Load Balancerze), należy zainstalować **Custom Metrics Adapter** (często nazywany Stackdriver/Google Cloud Metrics Adapter). Pozwala on HPA "widzieć" metryki z Cloud Monitoring (wcześniej Stackdriver). Liczba zapytań na sekundę (RPS) z Load Balancera jest doskonałym wskaźnikiem SLI dla warstwy frontendowej, pozwalającym na szybką reakcję na wzrost ruchu.

Analiza niepoprawnych odpowiedzi:
- **A: Configure HPA to use average response time from Liveness and Readiness probes:** Sondy Liveness i Readiness służą do sprawdzania, czy kontener żyje i czy jest gotowy do pracy, a nie do mierzenia wydajności czy obciążenia. HPA nie potrafi natywnie skalować w oparciu o czasy odpowiedzi tych sond.
- **B: Configure the vertical pod autoscaler (VPA) and enable cluster autoscaler:** VPA (Vertical Pod Autoscaler) służy do skalowania wertykalnego (zwiększanie CPU/RAM dla konkretnego poda), a nie do zwiększania liczby replik. Choć VPA jest przydatny, dla frontendu o dużym natężeniu ruchu zazwyczaj preferowane jest skalowanie horyzontalne (HPA). Cluster Autoscaler z kolei dodaje węzły (nodes) do klastra, gdy brakuje miejsca na nowe pody, ale nie decyduje sam o liczbie replik aplikacji.
- **D: Expose the NGINX stats endpoint and configure HPA:** Choć jest to technicznie możliwe (np. przy użyciu Prometheus i odpowiedniego adaptera), wymaga to znacznie więcej pracy konfiguracyjnej (eksponowanie statystyk, instalacja prometheus-adapter, konfiguracja scrape'owania) niż użycie gotowych metryk z GCLB, które już "płyną" do Cloud Monitoring.

Hity i triki (Hints & Tricks):
- Jeśli widzisz w pytaniu GKE + Load Balancer + skalowanie oparte na ruchu -> szukaj "Custom Metrics" lub "External Metrics".
- Pamiętaj: HPA = więcej podów, VPA = większe pody. Zazwyczaj nie stosuje się obu jednocześnie dla tej samej metryki (np. CPU), bo mogą ze sobą konkurować.
- Metryki z Load Balancera są traktowane jako "External Metrics" w HPA, ponieważ nie pochodzą bezpośrednio z obiektów wewnątrz Kubernetes.

Analiza i Podsumowanie Dyskusji (AI)

Pytanie sprawdza umiejętność wyboru odpowiedniej metody skalowania dla aplikacji webowej w GKE. Kluczowym elementem jest połączenie świata Kubernetes (HPA) ze światem infrastruktury Google Cloud (Cloud Load Balancing) poprzez metryki.

💡 Wskazówki i Triki (Exam Tips)

  • HPA to standard dla skalowania frontendów (skalowanie horyzontalne).
  • Aby skalować na podstawie metryk *spoza* klastra (jak GCLB), niezbędny jest "Custom Metrics Adapter".
  • Zawsze wybieraj metryki najlepiej odzwierciedlające obciążenie użytkowników (SLI) – RPS (Requests Per Second) jest tu klasykiem.

Question 70 / 201

Cloud Build

You use Cloud Build to build and deploy your application. You want to securely incorporate database credentials and other application secrets into the build pipeline. You also want to minimize the development effort. What should you do?

  • A. Create a Cloud Storage bucket and use the built-in encryption at rest. Store the secrets in the bucket and grant Cloud Build access to the bucket.
  • B. Encrypt the secrets and store them in the application repository. Store a decryption key in a separate repository and grant Cloud Build access to the repository.
  • C. Use client-side encryption to encrypt the secrets and store them in a Cloud Storage bucket. Store a decryption key in the bucket and grant Cloud Build access to the bucket.
  • D. Use Cloud Key Management Service (Cloud KMS) to encrypt the secrets and include them in your Cloud Build deployment configuration. Grant Cloud Build access to the KeyRing.
Show Suggested Answer
Suggested Answer: D 
Odpowiedź: D.

Wyjaśnienie:
Poprawna odpowiedź to D. Zarządzanie sekretami (takimi jak hasła do baz danych czy klucze API) w procesach CI/CD jest jednym z najważniejszych aspektów bezpieczeństwa w DevOps.

Dlaczego odpowiedź D jest poprawna:
1. Natywne wsparcie: Cloud Build posiada wbudowany mechanizm obsługi sekretów zaszyfrowanych za pomocą Cloud KMS. Możesz zdefiniować blok `secrets` w pliku `cloudbuild.yaml`.
2. Bezpieczeństwo "at rest": Nawet jeśli plik `cloudbuild.yaml` trafi do repozytorium kodu, sekrety są widoczne tylko jako zaszyfrowane ciągi znaków (ciphertext). Odszyfrowanie następuje dopiero w trakcie trwania buildu w bezpiecznym środowisku Google.
3. Kontrola dostępu: Dzięki IAM możesz precyzyjnie kontrolować, które konto serwisowe (Service Account) ma uprawnienia do korzystania z konkretnego klucza KMS (KeyRing/CryptoKey).

Analiza błędnych odpowiedzi:
- A: Przechowywanie sekretów w plikach tekstowych w Cloud Storage (GCS) jest ryzykowne. Każdy, kto ma dostęp do bucketu, może odczytać sekret. Szyfrowanie "at rest" w GCS jest przezroczyste dla użytkownika z uprawnieniami do odczytu obiektu.
- B: Przechowywanie klucza deszyfrującego w innym repozytorium to tzw. "security by obscurity". Jest to skomplikowane w zarządzaniu (wysoki Toil) i nie rozwiązuje problemu – nadal musisz jakoś zabezpieczyć dostęp do tego drugiego repozytorium.
- C: Szyfrowanie po stronie klienta (client-side encryption) przed wysłaniem do GCS wymaga dodatkowego kodu i zarządzania kluczami poza ekosystemem GCP, co drastycznie zwiększa wysiłek programistyczny (Development Effort).

Hity i triki (Exam Tips):
- Jeśli w pytaniu o sekrety pojawia się **Cloud KMS** lub **Secret Manager** – są to zazwyczaj najsilniejsi kandydaci na poprawną odpowiedź.
- Cloud KMS służy do **szyfrowania danych**, podczas gdy Secret Manager (nowsza usługa) służy do **zarządzania sekretami** jako takimi. W nowszych pytaniach Secret Manager jest częściej preferowany, ale na egzaminie mechanizm z KMS jest nadal bardzo popularny.
- Pamiętaj o używaniu zmiennych środowiskowych `secretEnv` w Cloud Build, aby nie przekazywać sekretów w argumentach linii komend (co mogłyby być widoczne w logach procesu).

Analiza i Podsumowanie Dyskusji (AI)

W nowoczesnych pipeline'ach CI/CD, takich jak te oparte na Cloud Build, unika się tzw. "hardcoded secrets". Wykorzystanie Cloud KMS do szyfrowania i odszyfrowywania w locie (just-in-time decryption) jest krokiem w stronę bezpieczeństwa zgodnego z zasadą Zero Trust.

💡 Wskazówki i Triki (Exam Tips)

  • Warto wspomnieć o **Secret Manager**, który jest obecnie rekomendowanym sposobem przechowywania sekretów w GCP (łatwiejsze wersjonowanie i rotacja).
  • Upewnij się, że konto serwisowe Cloud Build (`[PROJECT_NUMBER]@cloudbuild.gserviceaccount.com`) ma rolę `roles/cloudkms.cryptoKeyDecrypter`.
  • Nigdy nie loguj sekretów do konsoli podczas buildu! Cloud Build automatycznie maskuje niektóre wartości, ale dobra praktyka to świadome unikanie `echo $SECRET`.
